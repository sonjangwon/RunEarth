### 1. 파악 & 결정

- **기술 스택 확정**: Flutter(iOS·Android) + Supabase(서버리스 MVP) + Riverpod + go_router + Google Maps + **drift(로컬 DB)**, **local-first** 아키텍처

### 2. Flutter 앱 뼈대 구축

| 영역 | 내용 |
| --- | --- |

- **홈** — 여정(전주→부산)·스트릭·통계·CTA
- **기록** — 로컬 DB 연결(시드→조회), 필터·월별그룹·요약
- **달리기** — 상태머신(카운트다운→러닝→종료), 타이머 실작동
- **콘텐츠** — 테마런/마라톤 카드 + 상세
- **프로필** — 유저·통계·배지·설정

## 📝 기술 결정 / 향후 고려사항 메모

1. 서드파티 로그인 서비스로 계정을 인증하는 앱은 Sign in with Apple을 동등한 옵션으로 제공해야 한다는 게 App Store 가이드라인 4.8 > iOS 빌드엔 Sign in with Apple을 4번째 옵션으로 추가해야함
   https://developer.apple.com/app-store/review/guidelines/#login-services
2. 2026년 1월 1일부터 한국에 기반을 둔 개발자는 Sign in with Apple용 Services ID 등록/갱신 시 server-to-server 알림 엔드포인트를 제공해야 함 > 향후 인증 시 고려사항
3. 지도 SDK : Google Map (MVP)
   네이버를 하는 이유는 국내 상세 지도가 가능하기 때문이지만 뛰는 경로에 대한 선택으로 봐서는 Google Map도 충분하다고 생각함. Strava, Nike Run, Kyro 등 앱 역시 굳이 Naver를 하지 않음. Google이 앱에 연결하기 가장 안정적(예제/문서 등). 일단 MVP로 하고 향후 비용이나 데이터 고려할 예정
4. Flutter 상태관리 : Riverpod
   화면에 보이는 데이터(상태)가 바뀔 때, 그걸 어떻게 관리하고 화면에 반영하는지 결정하는 부분.
5. 러닝앱은 GPS 트래킹이 인터넷 없이도 안끊겨야하기 때문에 폰에 먼저 저장하고 인터넷이 되면 서버에 올리는 하이브리드 형태 . 그래서 러닝데이터는 기기 로컬에 우선 저장 + 서버에 동기화 대기 큐(후행처리)
