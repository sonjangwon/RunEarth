## 1. 로그인 직후 동기화 (`9feee7e`)

9/23 §6 에서 "한 줄짜리다, 다음에 고치자"로 미뤄둔 것.

`syncNow()` 호출 지점이 셋뿐이었다 — 앱 시작(**이미 로그인 상태일 때만**) ·
러닝 종료 · 재연결. **로그인을 막 끝낸 참은 어디에도 안 걸린다.** 스플래시는
이미 지나갔고, 게다가 그때는 로그인 전이라 `if (loggedIn)` 에서 건너뛴 뒤였다.

`signInWithGoogle()` 의 `ensureUserRow()` 뒤에 붙였다. 화면(login_screen)이
아니라 `AuthService` 에 둔 이유는 카카오·네이버가 붙어도 이 한 곳을 지나가기
때문이다. `unawaited` — 로그인 버튼 스피너가 업로드를 기다리면 안 된다.

**검증은 못 했다.** 밟으려면 로그아웃 → 기록 남기기 → 재로그인이 필요한데
오늘 그 경로를 타지 않았다. 정적 분석만 통과한 상태다.

## 2. GPS 품질 값 적재 (`1aa126d`) — 나가기 전에 넣어야 했던 것

9/23 §8 에 이렇게 남아 있었다:

> `Position.accuracy` 를 저장하지 않는다. 정확도로 거르는 게 더 정석인데
> 기록이 없어 임계값을 못 정했다.

**이걸 넣지 않고 트랙에 나가면 돌아와서도 임계값을 못 정한다.** 나가기 전에
재료를 챙기는 게 순서라 먼저 했다.

`LatLngPoint` 에 두 칸:

| 필드 | 뜻 | 단위 |
|---|---|---|
| `a` | GPS 정확도 — 기기가 알려주는 "이 반경 안쪽" | 미터(반올림) |
| `s` | **기기가 측정한 속도** — 도플러로 직접 잰 값 | cm/s |

### `s` 를 같이 넣은 이유 — 우리 속도 계산이 이중 오차다

지금 튐 필터는 **두 좌표의 거리÷시간**으로 속도를 낸다. 앞 좌표도 틀리고 뒤
좌표도 틀리면 속도는 더 크게 틀린다. GPS 는 **도플러로 속도를 직접 재고**, 그
값이 위치보다 정확하다. `geolocator` 의 `Position` 에 `speed`·`speedAccuracy` 가
이미 있는데 우리가 버리고 있었다.

한 번 나가서 두 방법을 비교하려면 둘 다 필요하다. 안 넣고 나가서 정확도가
답이 아니면 또 나가야 한다.

### 🔴 함정 — `hasAccuracy` 를 안 보면 필터가 거꾸로 돈다

`hasAccuracy`/`hasSpeed` 가 false 면 값이 **0.0 플레이스홀더**로 온다. 그대로
적으면 **'오차 0m = 완벽한 좌표'** 로 읽혀 나중에 필터가 반대로 동작한다.
패키지 문서가 직접 경고하고 있고, Mizutori 샘플의 `if (getAccuracy() <= 0)`
체크도 같은 이유다. **null 로 남긴다.**

### 외부 사례 (실제 소스를 받아서 확인했다)

검색 요약만 믿지 않고 저장소에서 파일을 받아 읽었다.

| 사례 | 정확도 임계값 |
|---|---|
| **OpenTracks** (오픈소스 트래커) | 기본 **50m** 초과 버림 (선택 10/20/30/50/100…) |
| **Mizutori 샘플** (러닝 전용) | **10m** |
| Avenza Maps | 32m |

OpenTracks 는 `GpsManager.onLocationChanged` 에서 진짜로 버린다 —
`if (!fulfillsAccuracy(threshold)) { Log.d("Ignore newTrackPoint. Poor accuracy."); return; }`.
같은 값으로 "GPS 신호 약함" 배지도 띄운다. **거리를 재는 용도는 10~30m 쪽이다.**

**구조가 우리와 거의 같았다 — 순서까지:**

| 단계 | OpenTracks | 우리 |
|---|---|---|
| 정확도 필터 | 50m | **없음** ← 오늘 준비한 것 |
| 최소 이동거리 | **10m** | **5m** |
| 구간 끊기 | 점 사이 200m 초과 | 30초 초과(시간 기준) |

**우리 최소 이동거리가 절반이다.** §8 에 남은 과다 계상의 후보지만, 9/23 의
"추정치 하나에 맞춰 조이면 과교정" 판단대로 **데이터가 나온 뒤에** 만진다.

Strava 공식 문서도 "지그재그가 직선으로 이어져 거리가 부푼다"고 인정하고,
불량 GPS 가 임계값을 넘으면 기기 거리와 섞어 재계산한다고 한다.
**완벽한 한 방은 없고 겹겹이 막는 게 정석이다.**

### 버린 좌표는 로그로만 남긴다

속도 상한에 걸린 좌표는 경로에 안 남아서 흔적이 없다.

```
[gps] 버림 — 126m / 7000ms (파생 18.0m/s · 기기 2.1m/s), 정확도 32m
```

`파생` 과 `기기` 가 크게 다르면 **위치는 튀었어도 속도는 멀쩡했다**는 뜻이고,
그러면 기기 속도 쪽이 더 나은 필터라는 근거가 된다. 반대로 정확도가 좋았는데도
튀었다면 **정확도 필터는 답이 아니라는 뜻**이고 그것도 알아둘 값이 있다.

최소 이동거리(5m)에 걸린 좌표는 **일부러 안 찍는다** — 제자리에 서 있으면 매
좌표가 걸려 로그가 밀려나고, 이쪽은 설계대로 버리는 것이다.

> **아무것도 거르지 않는다.** 임계값은 트랙 데이터를 보고 정한다.

## 3. 사진 모드 3단계 — Storage 보존 (`9d6d86b` `22a81b3`)

### 착수 전에 기대치를 맞췄다

9/23 §9-4 에 "지금은 로컬 전용이라 **기기를 바꾸면 사진을 잃는다**"고 적었는데
**이 작업으로 그게 해결되지 않는다.** 같은 노트 §5 에 답이 있었다:

> 동기화는 업로드만 한다 — 서버에서 되받는 경로가 없어서(`upsert` 뿐)

**기록 자체가 안 내려온다.** 기기를 바꾸면 기록이 통째로 비어 있어 사진이 붙을
데가 없다. 그래서 오늘의 성과는 **"나중에 복원 기능이 생겼을 때 꺼내 쓸 수
있도록 지금 보존한다"** 이다. 사진은 좌표로 복원할 수 없으니(경로 이미지와
다른 점) 지금 안 올리면 영구 소실인 건 맞다.

### 만든 것

| | |
|---|---|
| 버킷 | `run-covers` — private · 2MB · image/jpeg |
| 객체 경로 | `{auth.uid()}/{run_id}.jpg` |
| RLS | 첫 칸이 자기 uid 인 것만. **delete 정책 없음**(runs 와 같은 원칙) |

`cover_image_url` 에는 **URL 이 아니라 Storage 객체 경로**를 넣는다. private
버킷이라 공개 URL 이 없고 signed URL 은 만료돼 저장해둘 값이 아니다.

`isCoverPhoto` 와 파일 이름 규칙을 `services/storage/cover_storage.dart` 로
옮겼다. 동기화도 같은 판정이 필요한데 **`lib/services` 가 `lib/features` 를
import 한 전례가 없어** 그 방향을 만들지 않았다.

**화면에 안 걸려 있는 사진도 올린다.** 경로로 되돌려도 사진 파일은 남겨두는
정책(9/23)이라, "표시 중인 것만" 올리면 그 사진이 보존에서 빠진다.

**사진 파일이 사라졌으면 사진 없이 행만 올린다.** 예외를 던지면 사진 한 장
때문에 기록 업로드가 막히고 재시도를 무한히 돈다.

### 🔴 `markUnsynced` — §9-4 의 나머지 절반

사진을 등록해도 **재업로드를 타지 않았다.** `Run.toCompanion()` 에 `syncedAt`
이 없어서 `insertOnConflictUpdate` 가 그 칸을 SET 절에 안 넣고 옛 값이 남는다.

일부러 그렇게 둔 것이다 — 모델에 `syncedAt` 을 실으면 수정이 업로드 성공
표시를 덮어쓴다(`watchUnsyncedIds` 주석). 그래서 **"고쳤으니 다시 올려라"를
따로 말해주는** 메서드를 팠다.

### 문서 충돌 정정 (사용자 결정)

`offline-handling.md` 케이스 D 가 "대표 이미지 교체는 **오프라인 시 비활성화**"
라고 적혀 있었다. **케이스 C 와 같은 뿌리였다** — 2026-08-15 작성본의
local-first 확정 전 가정. (케이스 C 는 9/19 에 같은 이유로 이미 정정됐다.)

사진은 로컬에 즉시 저장되고 업로드는 큐를 타므로 막지 않는다. 다만
**"참가하기"(마라톤)는 원문대로 유지** — 차이는 *로컬로 완결되는 액션인가*
이고, 마라톤 참가는 서버에 자리를 잡는 일이라 완결되지 않는다.

### 🟢 실기기 검증 완료

대시보드 SQL 실행(사용자) → 디버그 빌드 설치 → 기록 상세에서 사진↔경로 토글.

| 확인 | 결과 |
|---|---|
| Storage 파일 생성 | 🟢 `run_1790162386904682.jpg` |
| 재업로드 트리거 | 🟢 `synced_at` 이 **15:10:40** 로 갱신 — 마지막 터치 시각과 일치 |
| 업로드 중 에러 | 🟢 없음 (`[cover]`·`[sync]` 로그 전무) |

### ⚠️ 기존 사진은 자동으로 안 올라간다

`markUnsynced` 는 **사용자가 대표 이미지를 바꿀 때만** 돈다. 9/23 에 이미
등록해둔 사진 3장은 전부 `synced=Y` 라 건드리지 않으면 영원히 서버에 안 간다.

**코드로 메우지 않기로 했다.** "기능이 생기기 전에 등록된 사진"이라는 일회성
상황이고 대상이 3건뿐인데, 백필 코드를 넣으려면 "이 사진이 이미 올라갔는지"를
로컬에 기록할 플래그를 새로 만들어야 한다. 3건 때문에 영구 코드를 남기는 건
과하다 (9/23 에 시드 기록을 앱 코드 대신 sqlite 로 넣은 것과 같은 판단).

→ **토글로 손수 백필한다.** 1건은 검증 겸 완료, **2건 남았다**
(`run_1790163117391072` · `run_1790166556405401`).

## 4. 기록 정렬이 거꾸로였다 (`16941c7`) — 사용자 발견

> "같은 날짜라도 마지막으로 뛴 게 맨 위에 올라가야 하는데 그렇게 동작하지
> 않는 것 같아."

맞았다. 폰의 09.23 기록 5건이 **먼저 뛴 것부터** 나열돼 있었다.

정렬이 `date` 하나뿐이었는데 그 값이 `"09.23"` **문자열**이다. 같은 날 기록은
정렬 키가 **완전히 같아** 순서가 정해지지 않고, SQLite 가 저장 순서(= 오래된
것부터)로 돌려준다.

### 같은 줄에 하나 더 있었다 — 연도를 안 본다

`"12.31"` > `"01.01"` 이므로 **해가 바뀌면 작년 12월 기록이 맨 위로 온다.**
데이터가 전부 2026년이라 안 드러났을 뿐, **1월 1일에 터질 것**이었다.

`year desc, date desc, id desc` 로 둘 다 고쳤다.

### `startedAt` 칼럼을 지금 안 만든 이유

마지막 칸은 **id 가 시각을 들고 있다는 데 기댄다**(`run_<micros>`). 취약한 걸
알면서 택했다 — 이 전제가 깨지는 시점과, `startedAt` 이 실제로 필요해지는
시점이 **둘 다 웨어러블 동기화**이기 때문이다.

- 워치에서 가져온 기록은 `run_<micros>` 규칙을 안 따른다 → 정렬이 깨진다
- `wearable-sync.md` 4 의 "시간대가 겹치는 워크아웃" 판정에 그 값이 필요한데,
  지금 `Run` 에는 **시작 시각이 아예 없다**

선을 두 번 그을 필요가 없어서 `wearable-sync.md` 4 에 🔴 **선행 조건**으로
적어뒀다. 기존 기록 백필은 id 에서 역산하면 되고, 기록이 늘어도 난이도는 같다.

### 🔴 뿌리 — 문서에 정렬 규칙이 아예 없었다

`records.md` 어디에도 정렬 얘기가 없었다. 코드 주석의 "최신순" 한 마디가 유일한
근거라 **어긋나도 알아챌 방법이 없었다.** 3-1 로 명문화했다.

## 5. 내가 만든 부수 효과 — 0km 기록 1건

검증하려고 앱을 실행했더니 기록이 **10 → 11건**이 됐다.

```
run_1790173730000000   09.23 (수)   0.0km   00:00   경로 없음
```

9/23 23:28 에 `active_runs` 에 남아 있던 **빈 스냅샷**이다. `restoreIfAny` 가
"6시간 넘음"으로 보고 `_finalizeExpired` 로 기록을 만들었고, 그게 서버로도
올라갔다. **의도된 동작**이지만 내가 앱을 안 켰으면 안 생겼을 기록이다.

### 🟡 그 과정에서 찾은 것 — 빈 스냅샷도 기록이 된다

`_finalizeExpired` 는 스냅샷 내용을 **보지 않고** 기록을 만든다. 0km·0초·좌표
없음이어도 만든다. 9/23 에 정한 **"0km 은 시간과 관계없이 미완료"** 와 어긋난다.
화면에서는 접혀서 안 보이지만 **DB 와 서버에는 쌓인다.** 앞으로도 러닝을
시작하자마자 앱이 죽으면 같은 게 생긴다.

거리와 좌표가 둘 다 비면 기록을 만들지 않고 스냅샷만 지우면 된다. **아직 안
고쳤다** — 오늘 작업 범위 밖이라 사용자에게 알리고 남겨뒀다.

## 6. 알게 된 것

- **`adb shell cat` 은 바이너리를 깨뜨린다**(9/23 §5 에 적어둔 그대로 또 밟았다).
  `adb exec-out` 을 쓰면 된다 — 9/23 의 `run-as cp` 우회보다 간단하다
- **arm64 디버그 빌드가 1121초** 걸린다. 백그라운드로 돌리되 출력을 `tail` 로
  넘기면 **진행률이 하나도 안 보인다**(파이프가 끝까지 버퍼링한다)
- 임계값 같은 건 **외부 사례를 먼저 찾는 게 빠르다.** 오늘 OpenTracks 소스에서
  정확도 50m·최소거리 10m·구간끊기 200m 를 확인하는 데 몇 분 걸렸다
