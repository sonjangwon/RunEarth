## 1. 🟢 절전 모드가 원인이었다 — 대조 측정으로 확정

사용자가 **절전 모드를 끈 상태로 다시 뛰고 와서** "정확하더라" 고 했다.
노트8 로컬 DB 를 `adb` 로 꺼내 9/26 기록과 나란히 돌렸다.

| 항목 | 09-27 (절전 **OFF**) | 09-26 (절전 **ON**) |
|---|---|---|
| 정확도 중앙값 | **4m** (3~7m) | 20m (최대 **533m**) |
| 10m 초과 좌표 | **0개** / 118 | 111개 / 167 |
| 샘플 간격 | **5초 고정**(최대 7초) | 중앙 4초, **최대 205초** |
| 30초 초과 끊김 | **0건** | 3건 |
| 30m 초과 점프 | **0건** | 19건 (최대 457m) |
| 속도 이상치 | **0건** | 25건 |
| 경로 합산 vs 저장 거리 | 차이 **2.8m** | 차이 825m |

경로 이미지(`route_*.png`)도 꺼내 눈으로 봤다. 9/27 은 곡선이 매끄럽고 꺾임이
전부 실제 길 모양이다. 9/26 은 삼각형 점프가 그림에 그대로 보인다.

**같은 기기·같은 빌드에서 절전 스위치 하나로 갈렸다.** 9/26 §14 의 추론이
대조군으로 확인됐다.

### 덤으로 확인된 것 둘

- **`stale` 로직이 설계대로 일하고 있었다.** 9/26 경로를 그냥 합산하면
  3.236km 인데 저장된 거리는 2.41km — **추적하지 못한 825m 를 정확히 뺐다.**
  다른 앱과 거리가 맞았던 게 우연이 아니라는 뜻이다.
- **밀린 기록 자동 업로드가 동작했다.** 9/26 21:39 에 끝난 기록의
  `synced_at` 이 **9/27 09:17** 이다. 11시간 38분을 밀려 있다가 올라갔고,
  로컬 17건 전부 `synced_at` 이 차 있다(미업로드 0건).
  **다만 그 러닝을 오프라인에서 끝냈는지는 기록에 안 남아** 완료 조건의
  앞부분은 못 닫았다. 비행기 모드 검증이 따로 필요하다.

> ⚠️ **절대 거리 정확도는 여전히 미판정이다.** 0.72km 라 기준 코스도 비교 앱도
> 없었다. 오늘 확인된 건 **좌표 품질과 경로 모양**이다.

## 3. 🟢 절전 모드 안내 (Android 9 이하)

원인이 확정됐으니 **우리가 코드로 고칠 수 없는 문제를 사용자에게 알린다.**
Strava 도 같은 대응을 한다(9/26 조사).

**`battery_plus` 를 쓰지 않고 MethodChannel 로 직접 갔다.** 호출이 한 줄이고,
버전 판정(`SDK_INT <= 28`)까지 같은 자리에서 끝나 의존성을 늘릴 값이 아니다.

- `MainActivity.kt` — `isPowerSaveBlocking` · `openBatterySaverSettings`
- `run_tracker.dart` — 같은 이름의 메서드 2개. 채널이 없으면(iOS·테스트)
  **조용히 false**
- `run_screen.dart` — START 전 **4번째 단계**(위치 → 알림 → 배터리 최적화 → 절전)

### 설계에서 하나 뒤집었다

원래는 "경고만 하고 그대로 START" 였는데, **'설정 열기' 를 고르면 START 를
멈추게** 했다. 끄러 보내놓고 그대로 시작하면 보낸 의미가 없다.
'그냥 시작' 은 바로 뛴다.

### 실기기 검증 (노트8, Android 9)

| 조건 | 결과 |
|---|---|
| 절전 ON + START | 안내 팝업이 뜬다 |
| '설정 열기' | 삼성 `BatterySaverSettingsActivity` 로 이동, START 안 함 |
| **절전 OFF + START** | **팝업 없이 카운트다운 시작** |

**세 번째가 핵심이다.** 뜨는 것만 봤으면 "조건과 무관하게 항상 뜨는 것" 일 수도
있었다. 카운트다운 중에 앱을 끊어 **찌꺼기 기록도 안 남겼다**(`runs` 17건 유지,
진행 중 스냅샷 0건). 테스트로 켠 절전 모드는 다시 껐다.

**제조사 자체 절전(삼성 '최대 절전')은 이 안내가 못 잡는다.** `isPowerSaveMode()`
는 안드로이드 표준 절전만 읽는다 — `run-flow.md` 6 의 [미검증] 항목은 그대로다.

## 4. 🟢 음성 안내 — 새 기능 (문서에 한 줄도 없었다)

사용자가 "출발할 때랑 1km 마다 음성 안내" 를 원했다. 기능 문서 전체에 음성·TTS
언급이 **0건**이라 규칙부터 만들어야 했다.

### 먼저 다른 앱을 찾아봤다

| | 안내 시점 | 읽는 내용 |
|---|---|---|
| Strava | 시작·정지·일시정지 + 구간(0.5/1km 선택) | 총 거리 · 직전 구간 페이스 · 평균 |
| Runkeeper | 거리 **또는 시간** 기준 | 10가지 중 선택 · 음량 · 목소리 · 수동 트리거 |
| 삼성헬스 | **1km 마다**(기본) | 누적 시간 + 평균 페이스 |

**1km 가 사실상 표준이고, 읽는 내용은 보통 세 조각이다.** 그리고 삼성헬스 문서에
결정적인 문장이 있었다 — *"음성 안내는 단말 시스템의 TTS 설정에 따른다."*
우리가 하려던 것과 같다.

**종료 멘트 원문을 공개한 앱은 없었다.** Strava 는 토글만 문서화하고 문구는 안
적는다. 그래서 **베낄 원문이 없어 우리가 정했다.** 판단 근거는 남의 앱이 아니라
**우리 화면에 뭐가 있느냐**였다 — 종료 요약 화면에 거리·시간은 크게 떠 있고
**여정 잔여 거리만 없다.**

### 확정한 문구 (말투는 `~습니다` 로 통일 — 사용자)

| 시점 | 멘트 | 실측 길이 |
|---|---|---|
| 출발 | `러닝을 시작합니다` | 1.38초 |
| 1km | `1킬로미터, 6분 28초` | 2.18초 |
| 2km 부터 | `2킬로미터, 구간 6분 28초, 평균 6분 41초` | 4.28초 |
| 종료 | `러닝을 종료합니다. 전주까지 142.6킬로미터 남았습니다` | 5.11초 |
| 도시 도착 | `러닝을 종료합니다. 전주에 도착했습니다` | 3.42초 |

처음엔 종료를 *"수고하셨어요…"* 로 썼는데 **사용자가 말투 섞임을 지적**했다 —
한 문장 안에서 "종료합니다"(합쇼체) 와 "남았어요"(해요체) 가 갈렸다.
기계 음성으로 칭찬을 들으면 어색하기도 해서 **사실형**으로 갔다.

### 구현에서 조심한 것

- **문구 조립은 순수 함수로 뺐다**(`voice_guide.dart`) → **테스트 14개**.
  기호(`6'28"`)나 `km` 가 문장에 섞이면 엔진이 이상하게 읽는데, 그건 들어보기
  전에는 모른다. **문장 단계에서 막는다.**
- **km 경계 시각을 보간한다.** 좌표가 경계에 딱 떨어지지 않아, 도착 좌표 시각을
  쓰면 구간이 길어지고 오차가 뒤로 밀린다. `km_splits.dart` 와 같은 방식으로
  맞췄다 — **음성과 화면이 다른 숫자를 말하면 그게 곧 버그 신고다.**
- **한 번에 2km 이상 넘기면 마지막 것만, 페이스 없이.**
- **종료 멘트의 여정 잔여 거리는 저장 *전* 값에서 이번 거리를 뺀다.**
  저장 뒤에 읽으면 DB 스트림이 돌았는지에 기대게 된다.
- **한국어 음성이 없으면 조용히 끈다.** 엔진 설치와 한국어 데이터는 별개다.

### 기기에서 실제로 들었다

`flutter_tts 4.2.5` 도입(사용자 승인). 구간 안내는 원래 1km 를 뛰어야 들리므로,
**디버그 전용 미리듣기**를 넣었다 — 달리기 탭의 러닝 타입 카드를 **길게 누르면**
다섯 문장이 이어서 나온다(9/26 §8 스와이프 미리보기와 같은 방식).

로그에서 확인된 것:

```
[LoadLanguage] kor-KOR-[f00]          ← f = female, 여성
Speed[100] Pitch[100]                 ← 시스템 기본값 그대로 (우리가 안 건드림)
Caller[10237-com.runearth.run_earth]
```

노트8 은 **삼성 TTS 엔진**(v3.5.01.69)이 기본이고 한국어 음성이
**'기본 음성 1' 하나뿐이라 성별 선택지가 없다.** Google TTS 도 깔려 있지만
선택돼 있지 않다.

🟡 **읽는 속도는 판단 보류.** 사용자가 "살짝 빠른 감" 이라고 했는데, 우리는
속도를 건드리지 않았고 로그상 `Speed[100]` — **기기 시스템 설정 그대로**다.
기기·엔진마다 체감이 다를 수 있어 **다른 기기에서 더 들어본 뒤 정한다.**

## 5. 🟡 날씨·미세먼지를 샘플 값으로 채웠다 (사용자 결정)

사용자가 "온도는 샘플이지? 미세먼지도 샘플로 반영해줄 수 있어?" 라고 물었다.
확인해보니 **두 카드가 반대로 놀고 있었다.**

| | 그전 상태 |
|---|---|
| 온도 | `24°`·`체감 26°` **하드코딩** — 주석도 없어 진짜처럼 보였다 |
| 미세먼지 | **일부러 `null`** — "불러오지 못했어요". 값을 지어내지 않는 쪽이 정직해서 |

**둘을 채우는 쪽으로 맞췄다**(A안 — "나중에 다시 업데이트하면 되니까").
제안했던 `kDebugMode` 한정(B안)은 택하지 않았다.

> ⚠️ **그래서 이 카드들은 시연에서 진짜처럼 보인다.** 개발용 더미 러닝 기록과
> 달리 **화면상 구분이 전혀 없다.** `feature-backlog.md` 에 경고를 박았고,
> 온도 쪽에도 없던 주석을 달았다.

## 6. 🟢 카드 두 장을 Figma 구조로 다시 맞췄다

미세먼지 샘플 값이 들어가자 **사용자가 바로 "Figma 랑 다르잖아" 라고 짚었다.**
`figma-alignment.md` 3번에 **미완료로 이미 적혀 있던 항목**이다 —
단서가 **"→ 기상청·에어코리아 연동 후"** 였다.

**값이 없어서 미뤄뒀던 건데, 같은 날 샘플을 넣으면서 그 전제가 사라졌다.**
체크박스는 그대로 두면 영원히 미완료로 남는 종류였다.

Figma Make 원본(`App.tsx` 678-685 · 904-930줄)과 대조한 결과:

| | Figma | 그전 우리 |
|---|---|---|
| 미세먼지 | pill 뱃지 + **그라데이션 게이지 + 흰 마커** + 4레이블 | 점 4개짜리 막대 |
| 날씨 | `날씨` 라벨 + **`☀️ 28°C 맑음` 한 줄** | 라벨 없이 `24°`/`체감 26°` 두 줄 |

### 문서와 Figma 가 충돌한 게 둘 나왔다 (결정 ⑥⑨)

| | 기능정의서 4-2 섹션 B | Figma | 결정 |
|---|---|---|---|
| 미세먼지 '나쁨' 이상 | **카드 배경**을 주황/빨강으로 | 배경 안 바꾸고 **pill 색만** | **Figma** |
| 날씨 카드 | 아이콘 + 기온 + **체감온도** | `☀️ 28°C **맑음**` | **Figma** |

CLAUDE.md 의 *"화면·비주얼은 Figma"* 와 9/20 결정 ②(미세먼지 색은 Figma)와 같은
방향이다. **기능정의서(2026-08-05)가 이제 ⑥⑨ 와 어긋난다**는 것도 함께 적어뒀다 —
문서만 읽은 사람은 버그로 오해한다.

### 모델에 숫자를 넣었다 (결정 ⑦⑧)

Figma 는 마커를 **`농도 / 150`** 위치에 놓는데, 우리 `AirQuality` 는 4단계 enum
뿐이라 **마커를 네 자리에만 찍을 수 있었다.** 그러면 그라데이션 게이지를 쓰는
의미가 없다. `AirQualityReading`(단계 + 농도)을 만들고 샘플을 Figma 와 같은
`보통 · 42` 로 맞췄다. 에어코리아 API 도 PM 수치를 주므로 연동하면 그대로 찬다.

**Figma 에 없는 농도 숫자를 화면에 함께 보여준다**(`미세먼지 42`) — 마커만으로는
'얼마나' 를 읽을 수 없다. 단위(㎍/㎥)는 좁은 카드에서 자리를 많이 먹어 뺐다.

배경을 안 물들이기로 하면서 `_MiniCard` 의 `background` 파라미터가 쓸 데가

## 14. 🔴 `env.json` 을 빼고 빌드해 **두 기기를 반쪽으로 만들었다**

사용자가 "휴대폰에 지금 버전 설치해줘" 라고 했고, `flutter build apk --release`
만 돌려서 설치했다. **`--dart-define-from-file=env.json` 을 빼먹었다.**

### 증상이 고약했다 — 앱은 멀쩡해 보였다

사용자가 먼저 발견했다: **"로그아웃이 안돼."**

연쇄는 이렇다.

1. `SupabaseConfig.isConfigured` 가 false → `main.dart` 의 `Supabase.initialize()`
   가 **통째로 건너뛰어진다**
2. `app_router.dart:111` — `if (!AuthConfig.gateEnabled || !SupabaseConfig.isConfigured) return null;`
   → **세션 가드가 꺼진다.** 로그인 화면으로 튕기지 않는다
3. local-first 라 로컬 DB 의 기존 기록이 그대로 보인다 → **로그인된 것처럼 보인다**
4. 로그아웃을 누르면 `_client.auth.signOut()` 이 초기화 안 된 `Supabase.instance`
   에 접근해 던진다

**빌드 로그에 경고가 없다. 앱도 안 죽는다.** 화면만 보고는 절대 못 찾는다.
동기화·계정 정보·사진 업로드도 같이 죽어 있었는데 아무 표시가 없었다.

### 찾은 방법 — 파일을 직접 본다

앱을 켜서는 알 수 없으니 **APK 안에 Supabase 호스트 문자열이 있는지 grep** 했다.

```
grep -a "<SUPABASE_URL 호스트>" app-release.apk   # 없음 → 미주입 확정
```

노트8 은 한 발 더 갔다 — 기기에 설치된 APK 를 `adb pull` 로 꺼내 **로컬
`app-debug.apk` 와 MD5 를 비교**했다. `536065201219d73d89883744a9521819` 로
**완전히 같았다.** 추측이 아니라 같은 파일인 걸 확인했다.

> `adb pull /data/app/...` 은 Git Bash 가 경로를 윈도우 경로로 바꿔서 실패한다.
> `MSYS_NO_PATHCONV=1` 을 앞에 붙여야 한다.

### 🔴 두 번째다

`feature-backlog.md` 에 **9/23 에도 `env.json` 누락으로 오프라인 검증을 못 했다**
고 적혀 있었다. 그런데 `CLAUDE.md` 의 '자주 쓰는 명령' 에는 `flutter run` 만
적혀 있었다 — **플래그가 빠진 채로.** 문서가 함정을 그대로 두고 있었다.

**고쳤다** (`CLAUDE.md` '자주 쓰는 명령'):

- 실행·빌드 명령에 `--dart-define-from-file=env.json` 을 붙여 적고, **왜 위험한지**
  를 섹션 맨 위 경고로 올렸다
- `flutter analyze` 는 env 가 필요 없다고 명시 — "전부 붙여야 하나" 로 헷갈리지
  않게
- **'실기기 설치' 항목 신설** — `adb install -r`(데이터 보존, `uninstall` 금지),
  `firstInstallTime` 확인법, 그리고 **설치 전 APK 에 env 가 박혔는지 grep 으로
  검증**하는 절차

노트8 에 설치할 때는 그 검증을 **먼저** 돌렸다. 순서를 바꾼 게 이번 수확이다.

### 빌드 정책을 정했다 (사용자 질문)

> "정식 배포하기 전까진 계속 debug 빌드로 해야 되지 않을까?"

**아니다.** debug 는 "배포 전 단계" 가 아니라 **개발 도구가 붙은 빌드**다.
JIT 라 느리고 CPU·배터리를 더 먹고 OS 에 더 잘 죽는다 — **지금 남은 검증이
하필 그걸 재는 것들이다**(트랙 거리 실측 · 배터리 · 백그라운드 생존 · 절전 대조).
debug 로 재면 숫자를 근거로 못 쓴다. APK 도 **221MB vs 62MB** 다.
그리고 **Play Console 은 `android:debuggable="true"` APK 업로드를 거부한다** —
베타 배포도 release 여야 한다.

**용도로 나눠 쓴다.** `build.gradle.kts:44` 에서 release 도 debug 키로 서명하므로
**서명이 같아 `adb install -r` 로 서로 덮어써도 데이터가 안 날아간다.**

| 용도 | 빌드 |
|---|---|
| 밖에서 뛰기 · 실측 · 배터리 · 백그라운드 · 남에게 보여주기 | **release** |
| 기능 개발 · 로컬 DB 열어보기 · hot reload | **debug** |

⚠️ **오늘 두 기기를 release 로 바꾸면서 `adb run-as` 가 막혔다** —
`run-as: package not debuggable`. 9/26 에 `geolocator_android` 버그를 잡은 게
DB 를 직접 읽어서였는데, **지금은 그걸 못 한다.** `synced_at` 이나 GPS 품질
컬럼을 봐야 하면 **env 를 넣은 debug 빌드**를 따로 설치해야 한다.

#### 🔻 "지금 debug 빌드를 만들어 두자" 는 틀린 제안이었다

위 ⚠️ 때문에 **"나중에 14분 기다리지 않게 지금 만들어 두자"** 고 제안했는데,
사용자가 되물었다 — *"다음에 또 기능 개발할 일 있으면 14분 또 기다려야 하는 거
아냐?"* 맞는 지적이고, **제안이 아낄 게 없었다.**

**14분은 변경할 때마다가 아니라 릴리스 APK 를 하나 뽑는 비용이다.**
개발할 때는 그 경로를 안 탄다.

| | 시간 | 측정 |
|---|---|---|
| 릴리스 APK 첫 빌드 | **850초 ≈ 14분** | `assembleRelease` 로그 |
| 릴리스 APK 증분 | 약 **9분** | 21:27 → 21:36 |
| `flutter run` 이후 hot reload | **1초 이내** | — |

릴리스가 느린 건 AOT 컴파일 + R8 때문이고 debug 는 둘 다 안 한다. 그리고
**`flutter run` 은 세션당 한 번만 빌드하고 붙어 있는다** — 수정할 때마다
빌드하지 않는다. 즉 **다음에 개발을 시작하는 순간 `flutter run` 이 debug 빌드를
기기에 알아서 올리고, DB 접근이 그때 공짜로 돌아온다.** 미리 만들 이유가 없다.

**미리 만들 가치가 있는 경우는 하나뿐이다** — PC 에 연결하지 않고 **밖에 나가서
뛰고 와서 DB 를 열어봐야 할 때**(`synced_at` 이 언제 찍히는지, GPS 품질 컬럼이
실제로 차는지). `flutter run` 은 USB 로 붙어 있어야 하니 그 경우엔 독립 실행되는
debug APK 가 필요하다.

그때 알아둘 것:

- **debug 로 뛰어도 좌표 자체는 같다.** 위치 수집은 네이티브 플러그인이 한다
- 망가지는 건 **배터리 · 체감 성능**, 그리고 **긴 러닝에서 OS 가 앱을 죽일 확률**
- 그래서 **"트랙에서 거리 실측"(할 일 §12-5)은 반드시 release**, **"DB 컬럼
  확인" 은 debug** 로 나눈다
