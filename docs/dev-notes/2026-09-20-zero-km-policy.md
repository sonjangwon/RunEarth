## 1. 0km 기록이 왜 어려운 문제였나

겉보기엔 똑같이 `0.00km` 인데 **성격이 전혀 다른 세 가지**가 섞여 있다.

| 유형 | 예시 | 실제 사례 |
|---|---|---|
| **A. 잘못 눌렀다 만 것** | START → 22초 뒤 STOP | `run_1789742870933776` (9/18 §5) |
| **B. 뛰었는데 GPS 를 못 잡은 것** | 1분 37초에 좌표 1개 | `run_1789297203613307` (9/13 §3-2) |
| **C. 진짜 짧은 러닝** | 400m 라 반올림하면 0.0 | 이론상 |

**A 는 쓰레기, B 는 절대 잃으면 안 되는 기록이다.** 그런데 데이터만 봐서는
둘 다 "거리 0, 시간 약간, 좌표 0~1개" 라 구분이 안 된다. 이게 이 결정을
9/13 부터 세 세션이나 미루게 만든 유일한 이유다.

### 그래서 시간을 두 번째 조건으로 넣었다

**판정: `km < 0.01` 그리고 `durSeconds < 60` — 둘 다 만족할 때만 '미완료'.**

시간 조건이 A 와 B 를 가른다. A(22초)는 걸리고 B(1분 37초)는 살아남는다.
거리 하나만 보면 B 까지 걸러내 버린다.

> 다른 러닝앱들은 아예 저장을 안 하는 듯하지만 **저장을 막는 건 반대**다.
> 막으면 B 가 통째로 사라진다 — "뛰었는데 앱이 안 세줬다"는 최악의 경험이고,
> 이 프로젝트가 지켜온 "기록은 잃지 않는다" 와도 어긋난다.
> **저장은 전부 하고, 세는 것과 보여주는 것만 조정한다.**

### 문서 충돌은 사실 없었다

`records.md` 4 의 "삭제 불가 — 영구 보존" 때문에 9/13 §3-4 가 "문서 정책과
충돌" 로 적어뒀는데, 다시 읽어보니 충돌이 아니다. 저건 **데이터를 지키자는
원칙**이지 **모든 걸 화면에 띄우라는 뜻이 아니다.** 저장해두고 표시에서만
거르는 건 위반이 아니다.

## 2. ⭐ 진짜 문제는 목록이 아니라 스트릭이었다

9/19 노트가 "목록이 지저분하다" 로 시작했지만, 코드를 열어보니 오염 범위가
훨씬 넓었다.

| 영역 | 상태 | 심각도 |
|---|---|---|
| 기록 목록 | 0km 카드가 쌓임 | 🟡 미관 |
| 홈 총 횟수 | `count: runs.length` — 전부 셈 | 🟠 |
| **스트릭** | **거리 조건이 한 줄도 없었음** | 🔴 |
| 홈 총거리·여정 진행도 | 0 을 더해도 0 | ✅ 무해 |

```dart
// 고치기 전 home_providers.dart
for (final r in runs) {
  final d = _runDate(r);
  if (d != null) ranDates.add(d);   // ← 기록이 있는 날 = 달린 날
}
```

**"매일 뛰었다"가 "매일 START 를 눌렀다"가 된다.** 목록이 지저분한 건 미관
문제지만 이건 앱의 핵심 동기 장치가 무력화되는 제품 문제다. 순서를 잘못
짚을 뻔했다.

## 3. 문서에 기준이 아예 없었다

`streak.md` §2 를 확인했더니 판정 기준이 "하루도 빠짐없이 매일 러닝" 한 줄이고
`StreakDay.ran` 은 그냥 `boolean` 이다. **최소 거리·시간 기준이 문서 어디에도
없다.** 충돌이 아니라 **공백**이었고, 그래서 구현이 "기록만 있으면 달린 날"로
간 것도 코드 잘못이 아니었다.

→ `records.md` §4-1 을 신설해 판정·근거·적용 범위를 한곳에 두고,
`streak.md` §2 는 그걸 참조하게 했다. 기준이 두 곳에서 갈라지지 않도록.

## 4. 구현

| 파일 | 변경 |
|---|---|
| `core/models/run.dart` | `RunCompleteness` 확장 — `isIncomplete` · `durSeconds` (코드 정본) |
| `home/data/home_providers.dart` | 통계·스트릭에서 제외 |
| `records/data/records_providers.dart` | `showIncompleteRunsProvider` (기본 false) |
| `records/presentation/records_screen.dart` | 기본 숨김 + 토글, 요약은 완료 기준 |
| `records/presentation/record_badges.dart` | `IncompleteRunChip` ('미완료', 무채색) |

### 구현하면서 정한 것 2가지

**① 요약 통계는 토글과 무관하게 항상 완료 기록만 센다.** 펼쳐 봤다고 총 횟수가
3→6 으로 늘면 어느 쪽이 진짜인지 알 수 없다. 토글은 **목록만** 바꾼다.

**② 기록이 전부 미완료여도 토글은 남는다.** 목록은 "아직 기록이 없어요"를
보이지만 그 위에 "미완료 러닝 N건 보기"가 떠 있다 — 앱이 기록을 **지운 게
아님**이 사용자 눈에 보여야 `records.md` 4 의 영구 보존이 지켜진 것으로 읽힌다.

펼쳤을 때 카드에는 무채색 '미완료' 칩이 붙는다(`PendingSyncChip` 과 같은 톤 —
성취가 아니라 상태다). 왜 접혀 있었는지 알 수 있어야 한다.

### 곁가지: `dur` 파싱이 복제돼 있었다

초 변환 코드가 `home_providers.dart` 와 `records_screen.dart` 에 **따로** 있었고
동작은 같은데 에러 처리가 미묘하게 달랐다(전자는 `?? 0` 폴백, 후자는 `continue`).
`durSeconds` 가 필요해진 김에 모델 확장 하나로 합쳤다. 세 번째 복제를 만들 뻔했다.

| 기록 | 거리 | 시간 | 판정 |
|---|---|---|---|

| `...870933776` 09.18 | 0.00km | 22초 | 미완료 |

| `...077406146` 09.19 | 0.00km | 27초 | 미완료 |
| `...113196441` 09.19 | 0.00km | 5초 | 미완료 |
| 나머지 4건 | 0.18~0.27km | - | 완료 |

### 검증 결과

| 확인 | 기대 | 결과 |

| 홈 총 횟수 | 10 → 5 | **5회** ✅ |
| 홈 총 시간 | 59초 감소(0h 12m → 0h 11m) | **0h 11m** ✅ |

날짜가 데이터에 없다).

### ✅ 상세 화면에도 '미완료' 칩을 붙였다

검증 중 카드에는 붙는데 상세로 들어가면 사라지는 걸 발견했다. 9/19 에 '동기화
대기' 뱃지를 카드와 상세 **양쪽**에 둔 선례가 있어 일관성이 어긋난다. 접혀
있던 기록을 열었을 때 이유가 화면에 남아 있어야 한다. 같은 세션에서 처리했다.

**달리기 종료 화면에는 붙이지 않았다.** `RunDetailView` 를 공유하지만
`headerTrailing` 은 기록 상세만 주입하므로 자동으로 분리된다 — 방금 자기가
끝낸 러닝에 '미완료' 를 바로 띄우는 건 과하다. 종료 화면은 그 자리에서
맥락이 있고, 판정도 저장된 `Run` 이 아니라 세션 상태로 다시 해야 한다.

| 확인 | 결과 |
|---|---|
| 미완료 기록 상세 | '일반' + '미완료' 칩 ✅ |
| 완료 기록 상세(0.21km) | 칩 없음 + 경로 렌더 정상 ✅ |

## 6. 날씨는 기상청으로 확정 — 붙이기 전 알아둘 것

9/19 §11-3 의 "어떤 API 를 쓸지" 가 **기상청**으로 정해졌다(위치 기반이어야
하므로). 다만 그대로 되는 게 아니다:

1. **미세먼지는 기상청에 없다.** 단기예보 API 는 기온·하늘상태·강수만 준다.
   미세먼지는 **에어코리아(한국환경공단)** 별도 API — data.go.kr 한 계정이지만
   **서비스마다 따로 활용신청**해야 한다. 기능정의서 4-2 섹션 B 의 4단계
   상태 바를 살리려면 둘 다 필요하다.
2. **위경도를 그대로 못 쓴다.** 기상청은 **격자(nx, ny)** 를 받는다 —
   람베르트 정각원추도법 변환이 필요(공개 공식, 30줄 정도).
   에어코리아는 또 **TM 좌표 → 근접 측정소 조회**로 방식이 다르다.

### 결정: API 키는 `env.json` 에 둔다 (사용자 결정 2026-09-20)

Edge Function 프록시도 검토했으나 **MVP 단계에 프록시부터 세우는 건 과하다**는
판단. 공공데이터 키는 유료 크레딧이 붙지 않아 노출 시 피해가 "호출 한도 소진"
수준이고, 나중에 프록시로 옮기는 건 호출 지점 한 곳만 바꾸면 된다.

> ⬜ **`http` 패키지 추가 확인 필요** — 지금 pubspec 에 없다. 문서에 없는
> 패키지라 착수 전 질문. `dart:io` 의 `HttpClient` 로 패키지 없이도 되지만
> 코드가 길어진다(웹 지원이 막히나 이 앱은 iOS·Android 전용이라 무해).

## 7. ✅ 흰 런치 화면 — 고쳤다 (`4320eb0`)

9/19 가 놓친 곳이 하나 더 있었고, **Android 12+ 는 아예 다른 속성을 본다**는
게 이번 작업의 핵심이었다.

9/19 §5 는 `values/styles.xml` 의 `LaunchTheme` parent 만 지목했는데,
확인해보니 `drawable/launch_background.xml` 은 아예 **하드코딩**이다:

```xml
<item android:drawable="@android:color/white" />
```

`drawable-v21/` 쪽은 `?android:colorBackground`(테마 추종)라 9/19 분석대로지만,
v21 미만 폴백은 테마와 무관하게 무조건 흰색이다. 고칠 때 **둘 다** 봐야 한다.

### 이번 세션 스크린샷에 실제로 찍혔다

검증 중 앱 시작 직후를 캡처했더니 **아이콘 주위가 전부 흰색**이었다(에뮬레이터가
라이트 모드였다). 9/19 는 "고치면 좋겠다" 수준으로 적었지만 **실물 증거가 나왔다.**
다크 앱을 켤 때마다 흰 화면이 번쩍이고 있다.

### ⭐ parent 만 바꿨으면 안 고쳐졌다

**Android 12+ 는 `windowBackground` 를 보지 않는다.** SplashScreen API 가
`windowSplashScreenBackground` 를 따로 읽는다. 이 속성을 넣지 않으면
LaunchTheme parent 를 Black 으로 바꿔도 스플래시는 흰색으로 남는다.
검증 기기가 API 35 라 실제로 이 경로를 탔다.

낮은 API 는 모르는 테마 속성을 무시하므로 `values-v31/` 로 분기하지 않고
`values/` · `values-night/` 양쪽에 그냥 뒀다. (분기하면 다크 모드에서
`values-night` 가 `values-v31` 보다 우선해 속성이 누락되는 함정도 있다 —
리소스 우선순위에서 night 가 버전보다 앞선다.)

### 고친 내용

| 파일 | 변경 |
|---|---|
| `values/colors.xml` **신규** | `launch_background` = `#070911` |
| `values/styles.xml` | parent `Theme.Light` → `Theme.Black`, 12+ 속성 추가 |
| `values-night/styles.xml` | 12+ 속성 추가 (양쪽 동일하게) |
| `drawable/launch_background.xml` | 하드코딩 `white` → `@color/launch_background` |
| `drawable-v21/launch_background.xml` | `?android:colorBackground` → 색상 참조 |

색을 `colors.xml` 한 곳에 모은 이유: 디자인 토큰 `background` 와 **값이
어긋나면 앱이 뜨는 순간 배경색이 한 번 바뀐다.** 네 파일에 색을 흩뿌리면
다음에 토큰이 바뀔 때 반드시 하나를 빠뜨린다.

### 검증

| 확인 | 결과 |
|---|---|
| 라이트 모드(`cmd uimode night no`) 런치 픽셀 | **`#070911`** ✅ |
| 다크 모드(`night yes`) 런치 픽셀 | **`#070911`** ✅ |
| 앱 정상 부팅 | 홈 렌더 · 0km 정책 유지 ✅ |

> 픽셀은 스크린샷에서 직접 뽑아 비교했다. "어두워 보인다"가 아니라 **토큰과
> 같은 값인지**가 중요하다 — `Theme.Black` 의 기본 배경은 `#000000` 이라
> 눈으로는 구분이 안 되지만 앱 배경과 다르다.

## 9. ✅ 미세먼지 4단계 상태 바 (`f7372cb`)

9/19 §6-① 이 "🔴 하드코딩"으로 잡아둔 것 중 **UI 쪽 절반**을 닫았다.
기존 카드는 `'보통'` 이라는 문자열 리터럴 하나가 전부였고, 문서가 정의한
4단계 바도 배경색도 **아예 없었다**(기능정의서 4-2 섹션 B).

### 색은 에어코리아 표준을 따른다 (사용자 결정 2026-09-20)

| 단계 | 색 | 기존 토큰 |
|---|---|---|
| 좋음 | 파랑 `#3B82F6` | 러닝 타입 '테마' 와 같은 값 |
| 보통 | 초록 `#00E87A` | primary |
| 나쁨 | 주황 `#FF5F1F` | accent |
| 매우나쁨 | 빨강 `#EF4444` | 스트릭 7일과 같은 값 |

앱 토큰 계열(초록→주황→빨강)로 갈 수도 있었지만, **네 색이 이미 전부 토큰에
있어서** 표준 색계를 써도 팔레트가 늘지 않는다. 기상·대기 앱 어디서나 같은
의미로 쓰이는 색이라 사용자가 새로 배울 게 없다.

### 배경색은 '나쁨' 이상에서만 켠다

문서가 그렇게 정의하기도 했고, **좋음·보통까지 물들이면 경고가 일상이 되어
정작 나쁜 날에 눈에 안 띈다.**

### 🟡 값은 여전히 없다 — 그래서 없다고 말한다

미세먼지는 기상청이 아니라 **에어코리아** 소관이고 키가 아직 없다(§6).
값을 하드코딩하는 대신 `airQualityProvider` 로 분리하고 `null` 을 준다.
`null` 은 `offline-handling.md` §2-A 가 **이 카드에 정확히 지정한**
"불러오지 못했어요" 상태다. 연동할 때 provider 만 갈아끼우면 된다.

> "다시 시도" 버튼(`global-states.md` 인라인 에러 패턴)은 붙이지 않았다 —
> 재호출할 요청 자체가 없어 누르면 아무 일도 하지 않는 버튼이 된다.
> 9/19 의 '대표 이미지 변경' 버튼과 같은 판단이다.

### 검증하면서 바를 키웠다

처음 만든 바(8×4, 간격 3)는 **하이픈처럼 보여 단계 바로 읽히지 않았다.**
11×6, 간격 4 로 키우니 채운 칸과 빈 칸이 분명해졌다.

| 확인 | 결과 |
|---|---|
| 매우나쁨 | 4칸 빨강 + 붉은 배경 ✅ |
| 나쁨 | **3칸 주황 + 4번째 칸 회색** + 주황 배경 ✅ |
| 기본(null) | 중립 아이콘 + "불러오지 못했어요", 배경 중립 ✅ |

> ⚠️ 좋음·보통은 **화면으로 확인하지 못했다.** provider 가 null 이라 임시로
> 값을 주입해야 보이는데, 빌드 1회씩이 든다. 같은 코드 경로에 상수만 다르다.
> 임시 주입값은 커밋 전에 되돌렸고 `TEMP-VERIFY` 잔여가 없음을 확인했다.
