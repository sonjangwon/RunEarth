## 1. 로그아웃 (`54718e8`) — 9/25 §11-5 의 첫 칸

`AuthService.signOut()` 은 **이미 있었다.** UI 에만 안 붙어 있었다.
로그인 화면 이동도 라우터 세션 가드가 `onAuthStateChange` 를 듣고 있어
따로 짤 게 없었다. 화면에서 또 `go()` 하면 둘이 경쟁한다.

### 🔴 그런데 `signOut()` 이 앱 재시작 후엔 실패하고 있었다

```dart
Future<void> signOut() async {
  await GoogleSignIn.instance.signOut();   // ← 여기서 던진다
  await _client.auth.signOut();            // ← 도달 못 함
}
```

google_sign_in v7 은 쓰기 전에 `initialize()` 가 필요하고, 그걸 부르는
곳이 `signInWithGoogle()` **하나뿐**이다. 플래그는 인스턴스 필드라 앱을
껐다 켜면 false 로 돌아간다.

**그런데 Supabase 세션은 30일 슬라이딩이라 사용자는 대개 로그인 화면을
거치지 않고 앱을 켠다.** 즉 로그아웃이 동작하는 유일한 경우가 "방금 로그인한
세션에서 바로 로그아웃" 이었다 — 실제로 누르는 상황과 정확히 반대다.

구글 캐시 정리를 try 로 감쌌다. **두 작업의 중요도가 다르다** — 앞엣것은
"다음에 계정 선택 화면을 다시 보여주기" 정도의 편의고, 뒤엣것이 로그아웃
그 자체다.

하위 화면이 셋이라 제목줄·여백·뒤로가기를 `settings_page.dart` 에 공용으로

### 닉네임 — [미확정] 두 개를 닫았다 (사용자 결정)

길이는 `runes` 로 센다. `'🏃'.length` 는 **2** 라 이모지 6개짜리가 "12자

**규칙을 테스트로 걸었다**(`nickname_validation_test.dart`, 6개).

이 경우다.

전역 반영은 `ref.invalidate(currentAppUserProvider)` 한 줄로 끝났다 —
홈·프로필·계정 정보가 모두 같은 provider 를 본다.

**오프라인에서는 저장을 막는다.** 대표 이미지(9/25 정정)와 달리 이름은
로컬 미러가 없어 서버 말고 적어둘 데가 없다.

### 권한 화면 — 여기서 권한을 요청하지 않는다

위치 권한은 START 에서 묻기로 돼 있고(`run-flow.md` 6), 9/25 전수 감사에서
"로그인 직후 권한 팝업" 조건 2건을 취소선으로 정정한 것도 같은 이유였다.
**설정 화면을 구경만 해도 팝업이 뜨면 그 정책과 정면으로 어긋난다.**

`AppLifecycleState.resumed` 에서 다시 읽는다. 이게 없으면 설정에서 방금 켠
권한이 계속 '꺼짐' 으로 보여 화면의 존재 이유가 사라진다.

## 3. 회원탈퇴 (`39c8659`) — 만들었더니 기존 결함이 드러났다

### 🔴 `ensureUserRow()` 가 자동 복구를 안 하고 있었다

```dart
if (existing != null) return;   // 행이 있으면 아무것도 안 함
```

이건 **의도된 설계**였다 — 주석에 "로그인할 때마다 구글 이름으로 덮어쓰지
말 것" 이라고 적혀 있다. 그런데 그게 `deleted_at` 까지 손대지 않게 만들었다.

```
탈퇴 → deleted_at 찍힘 → (3일 뒤) 재로그인 → 행 있음 → return
     → deleted_at 이 남은 채로 앱을 정상 사용
```

`profile-settings.md` 4 가 정한 "탈퇴 대기 → 재로그인 시 자동 복구" 가
그냥 일어나지 않는다. 겉보기엔 멀쩡한데 서버엔 탈퇴 대기로 남아, **나중에
pg_cron 배치가 붙는 순간 잘 쓰던 계정이 30일째에 삭제된다.**

컬럼과 상태표는 8/15 부터, 마이그레이션은 9/12 부터 있었는데 **읽는 코드만
없었다.** 탈퇴를 만들었기 때문에 드러났다.

### 🔴 순서가 결과를 바꾼다 — 그리고 에러가 안 난다

RLS 는 `auth.uid() = id` 다. 세션을 먼저 지우면 `auth.uid()` 가 null 이라
UPDATE 가 아무 행에도 안 맞는데, **PostgREST 에서 RLS 로 걸러진 UPDATE 는
예외가 아니라 "0건 수정" 으로 조용히 성공한다.** try/catch 로도 안 잡힌다.

그래서 **소프트 삭제 → 세션 삭제** 순서다. 전체 기기 무효화는
`signOut(scope: SignOutScope.global)` — `session-policy.md` 4 의
[미확정]("로그아웃은 해당 기기, 탈퇴는 전체") 을 기본 가정대로 확정했다.

### 결정 2건 (사용자)

- **로컬 DB 기록은 지우지 않는다.** 30일 안에 같은 기기에서 재로그인하면
  기록이 그대로 돌아와야 복구가 진짜 복구가 된다
- **30일이 지나도 그냥 복구한다.** 영구삭제 배치가 없어 데이터가 안 지워졌는데
  로그인만 막으면 사용자가 복구도 재탈퇴도 못 하고 갇힌다

두 번째는 **체크가 아니라 🟡 미결로 적었다.** 배치가 생기면 없앨 예외라,
체크하면 다음 사람이 "30일 정책 구현됨" 으로 읽는다.

## 4. 스켈레톤 · 인라인 에러 (`5c67f8a`)

`core/widgets/` 를 새로 만들었다(CLAUDE.md 폴더 구조에도 적음).

### 🔴 홈이 로딩 중과 "기록 없음" 을 구분하지 않고 있었다

```dart
final all = ref.watch(runsStreamProvider).valueOrNull;
if (all == null) return HomeStats.empty;   // 로딩 중도 '0'
```

집계 셋(`homeStats`·`journey`·`streak`)을 `AsyncValue` 로 바꾸면 홈·프로필·
기록의 숫자 계산이 전부 걸린다. 그래서 집계는 그대로 두고
**`runsLoadingProvider` 를 따로 파서 "뼈대를 세울지" 만 별도로 판단**하게
했다.

이게 이론이 아니었다는 게 §10 에서 드러난다 — 실기기 콜드 스타트에서
**약 10초** 동안 뼈대가 보였다. 안 넣었으면 그 10초가 전부 `0km` 였다.

### 🔴 위젯 테스트가 깨졌고, 그게 맞는 신호였다

펄스가 `repeat(reverse: true)` 라 **`pumpAndSettle` 이 영원히 안 끝난다.**
`pump(Duration)` 으로 바꾸면서 스플래시 최소 노출(800ms)도 손으로 넘기게
했다. 앞으로 뼈대가 보이는 화면을 테스트할 때마다 밟을 함정이라 문서에
🔴 로 박았다.

### 남긴 것

**로컬 DB 읽기에 타임아웃이 없다.** 스트림이 값도 에러도 안 주면 뼈대에
영원히 머문다. 기기에서는 drift 가 빈 테이블이어도 빈 목록을 즉시 주므로
재현되지 않지만, **위젯 테스트 환경이 실제로 그 상태다.** 🟡 로 적었다.

## 5. START 위치 권한 3단계 (`7f90abc`) — 판단을 한 번 뒤집었다

처음엔 "오늘 트랙에 나갈 거라 러닝 시작 경로는 건드리지 말자" 고 했는데,
코드를 보니 **허용된 경로는 손댈 필요가 없었다.**

```dart
var permission = await Geolocator.checkPermission();
if (permission == LocationPermission.denied) { ... }  // 거부일 때만
return true;                                           // 허용이면 바로 여기
```

폰은 이미 권한이 허용돼 있어 거부 분기를 아예 안 밟는다. 그래서 했다.

### 순서를 바꿨다

기존은 알림 → 절전 → `start()` 안에서 위치였다. 그러면 **다 허락해놓고
마지막에 "시작할 수 없어요" 를 본다.** 위치를 맨 앞으로 옮겼다.

### 2차 안내에서 시스템 다이얼로그를 다시 부르지 않는다

문서 §3 의 플랫폼 제약대로 한 번 거부하면 팝업이 안 뜨고 즉시 거부가
돌아온다. 부르면 **사용자 눈에는 아무 일도 안 일어난 것처럼** 보인다.
앱 모달 + `openAppSettings()` 만 쓴다.

### [미확정] 2건을 질문 없이 정리했다 — 답이 문서 안에 있었다

| 항목 | 정리 |
|---|---|
| 플래그를 세션/영구 중 어디에 둘지 | §8 마지막 완료 조건이 "팝업 닫고 다시 START 하면 2차부터 반복" 으로 정해놨다. 리셋되니 **저장할 상태가 없다** |
| 재로그인 시 1차 다이얼로그 재노출 | 9/25 에 **1차 요청 자체가 폐기**됐다. 물음이 성립하지 않는다 |

9/25 §13 의 "규칙이 문서에 없어서 못 맞춘" 것과 **반대 경우**다. 이번엔
문서가 답을 갖고 있었고 `[미확정]` 딱지만 낡아 있었다.

`LocationPermissionState`(enums.dart)를 처음으로 실제로 썼다. 8/15 부터
문서와 코드에 있었는데 아무도 안 쓰고 있었다.

## 8. 스와이프 미리보기 (`997987e`) — 테스트 전용

22개를 다 확인하려면 **19,432km 를 달려야 한다.** 카드를 좌우로 넘기면
다른 도시 배경을 미리 보게 했다.

- 짧게 밀면 한 칸, 길게 끌면 여러 칸(56px/칸)
- 미리보기 중엔 오렌지 `미리보기 (테스트)` + 도시명, `n / 22`,
  '실제로 돌아가기'
- **진행률·거리 등 실제 데이터는 건드리지 않는다**

**`kDebugMode` 에서만 동작한다.** 실서비스에서 카드를 넘길 수 있으면 아직
도달하지 않은 도시를 미리 보게 돼 "달린 만큼 나아간다" 는 전제가 깨진다.

### 속도가 아니라 끈 거리로 센다

처음엔 `primaryVelocity` 로 만들었더니 실기기에서 `adb input swipe` 를
통째로 놓쳤다. 천천히 미는 손가락도 같은 이유로 놓친다. 거리 기준이면
끌고 있는 동안 연속으로 넘어가 22개를 훑기에도 낫다.

### 🔧 원복 방법

**이 커밋(`997987e`) 하나만 되돌리면 깨끗하게 사라진다.** 같이 빠지는 것:
스와이프 제스처 · 미리보기 배지 · `JourneyProgress.toCityIndex`(이 기능만
쓴다) · `journey.md` §4 의 테스트용 문단. 배경 이미지 22개와 전환 로직은
다른 커밋(`bc15612` `9e60f7b`)이라 그대로 남는다.

릴리즈 빌드엔 이미 안 들어가므로 급하지 않다. 다만 **디버그 빌드로 남에게

## 12. 🔴 GPS 품질 값이 안드로이드에서 **항상 null** 이었다 (`1086d59`)

차로 앱을 켜놓은 게 이걸 잡았다. 좌표 125개 전부 `a`·`s` 가 null 이었다 —
**9/25 에 만든 `1aa126d` 가 이 기기에서 아무것도 담고 있지 않았다.**
그대로 트랙에 나갔으면 돌아와서 데이터가 하나도 없었을 것이다.

### 원인 — 우리 코드가 아니라 플러그인

`geolocator_android` 5.0.3 의 `AndroidPosition.fromMap` 이
`Position.fromMap` 으로 플래그를 **올바르게 계산해놓고**, 새 객체를 만들면서
값만 복사하고 `hasAccuracy`/`hasSpeed` 를 안 넘긴다. 생성자 기본값이 false 라
**안드로이드에서는 두 플래그가 영원히 false** 다.

```dart
final position = Position.fromMap(positionMap);   // 플래그 정상
return AndroidPosition(
  accuracy: position.accuracy,     // 값은 복사
  speed: position.speed,
  // hasAccuracy / hasSpeed 는 안 넘긴다  ← 여기서 사라짐
);
```

**속도와 무관했다.** 차 주행(92개)뿐 아니라 걷는 속도로 기록해 필터를 통과한
33개도 전부 null 이었다.

### 고친 방법 — 플래그 대신 값

`LocationMapper.toHashMap`(Java)이 `location.hasAccuracy()` 일 때만 키를 넣고,
키가 없으면 Dart `_toDouble` 이 0.0 을 채운다. 그래서 값으로 판단할 수 있다.

- 정확도: `> 0` — `0` 은 물리적으로 말이 안 된다
- 속도: **`0` 이 정상값**이라(서 있으면 0) 값으로 못 거른다. `speedAccuracy` 를
  본다 — 도플러 신뢰도를 줬다는 건 속도도 쟀다는 뜻이다

진단 로그(앞 5개 좌표의 원시값)를 같이 넣었다. **확인이 끝났으니 `_rawLogCount`
와 함께 지울 것.**

거르면 **실제로 지나간 경로가 사라진다.**

| 임계값 | 없음 | 70m | **50m** | 30m | 10m |
|---|---|---|---|---|---|

| 실측 대비 | +7% | -12% | **-23%** | -39% | -85% |

**OpenTracks 의 50m 를 그대로 가져오면 23% 짧아진다.** 9/25 에 "외부 사례를

## 14. 🔴 노트8이 3분 25초 끊긴 진짜 이유 — 절전 모드

기기 차이가 압도적이었다.

| | 노트8 (2017) | 갤S24 (2024) |
|---|---|---|
| 정확도 중앙값 | 20m | **3m** |
| 최대 | **533m** | **13m** |
| 좌표 간격 | 8~12초 | 4.3초 |
| 20초+ 공백 | **6번** (최대 **205초**) | 1번 (45초) |
| 100m 초과 점프 | 4건 | **0건** |

```
21:24:54  마지막 좌표 (정확도 12m)   ← 화면 끔
   ...    205초 완전 공백
21:28:19  첫 좌표 (정확도 533m)      ← 화면 켬, GPS 콜드 재획득
```

끊기기 직전이 **12m 로 좋았다.** 신호가 나빠진 게 아니라 **OS 가 꺼버린 것**이다.
같은 시각 같은 코스에서 S24 는 멀쩡했으니 **환경 탓도 아니다.**

### 원인 — 절전 모드 (Android 9)

```
Android 버전       : 9
low_power          : 1  ← 절전 모드 켜짐
앱 대기 버킷       : 5 (EXEMPTED)
deviceidle whitelist: 등록됨
```

**절전 제외(doze whitelist)는 이미 걸려 있었다.** 그건 백그라운드 작업 제한을
푸는 것이고, **절전 모드의 위치 차단은 별개**다. Android 9 이하는
**절전 모드 + 화면 꺼짐 → 위치 서비스 정지**이며 앱이 못 막는다.

사용자 가설("백그라운드로 돌게 안 했을 땐 이런 일 없었다")이 맞았다 — 예전엔
화면을 켠 채 뛰었으니 걸리지 않았다.

**Android 10 부터는 이 동작이 없다.** S24(Android 16)에선 해당 없다.

### 다른 앱도 같다

Strava 가 이 문제로 도움말을 여러 개 운영하고 제조사별 안내까지 둔다 —
"Power Saving Mode 를 끄라". **OS 제한이라 앱이 우회할 수 없고**, 업계 표준
대응이 사용자 안내다. 다만 삼성헬스처럼 **걸음 수를 섞는 앱은 덜 당할 수
있다**(위치가 끊겨도 센서로 추정) — 이건 아직 확인 못 한 추론이다.

### 조치

폰의 절전 모드를 껐다(`settings put global low_power 0`). 자동 켜짐 임계값이
`0` 이라 직접 켜지 않는 한 다시 안 켜진다.

## 18. 오늘 배운 것

9/25 는 "문서가 실제와 어긋난 게 다섯 번" 이었다. 오늘은 **반대 방향**이
나왔다.

| | 무슨 일 | 뿌리 |
|---|---|---|
| §5 | `[미확정]` 2건이 이미 답이 나와 있었다 | 완료 조건이 답을 정해뒀는데 **[미확정] 딱지만 낡아 있었다.** 어제 규칙을 박은 효과로 이번엔 문서를 먼저 읽어서 찾았다 |
| §3 | 탈퇴를 만들었더니 `ensureUserRow` 결함이 드러났다 | 컬럼·문서·마이그레이션은 8/15~9/12 부터 있었고 **읽는 코드만 없었다.** 기능을 끝까지 만들어야 드러나는 종류다 |
| §4 | 테스트가 깨진 게 **맞는 신호**였다 | 무한 애니메이션은 `pumpAndSettle` 과 상극이다. 테스트를 고치는 게 아니라 함정을 문서에 적는 게 답 |

그리고 하나 더:

- **§7 — 200 응답은 "쓸 만하다" 가 아니다.** URL 이 산다는 것만 확인하고
  넘어갔으면 인천에 정체불명 야경이, 프리토리아에 하늘 사진이 들어갔다.
  **눈으로 보는 단계를 건너뛰면 "확인했다" 가 거짓이 된다.**
- **§5 — 내 판단을 뒤집는 것도 근거가 있어야 한다.** 아침엔 "러닝 경로를
  건드리지 말자" 고 했는데, 코드를 보니 허용 분기는 손댈 필요가 없었다.
  조심하는 쪽으로 틀린 것도 틀린 것이다.

### 저녁에 더 나온 것

- **§12 — 기능을 만들어놓고 값이 들어오는지 안 봤다.** 9/25 에 GPS 품질 적재를
  만들고 "정적 분석 통과" 로 넘겼는데, 실제로는 **한 개도 안 담기고 있었다.**
  차로 앱을 켜놓은 우연이 아니었으면 트랙에 나갔다 헛걸음할 뻔했다
- **§13 — 내가 만든 기준값이 틀릴 수 있다.** 도플러 적분을 "정답" 으로 놓고
  "거리가 35% 부풀었다" 고 단정했는데, 실측(다른 앱 2.39km)이 나오자
  **우리가 0.84% 로 맞았다.** 틀린 건 내 기준이었다. 기준값을 세울 때
  그게 왜 정답인지부터 따졌어야 했다
- **§13 — 남의 임계값을 그대로 옮기면 안 된다.** 9/25 에 "외부 사례를 먼저
  찾는 게 빠르다" 를 배웠는데, 이번엔 OpenTracks 의 50m 를 그대로 쓰면
  **거리가 23% 짧아진다.** 사례는 출발점이지 답이 아니다
- **§14 — 증상을 고치기 전에 원인을 찾아야 한다.** 경로가 튀는 걸 보고
  "정확도 필터를 넣자" 로 갔는데, 실제 원인은 **절전 모드**였다. 필터를
  먼저 만들었으면 원인을 덮은 채 증상만 가렸을 것이다
