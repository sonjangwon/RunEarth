## 0. 시작 시점 상태

9/14 노트 §5의 검증 표가 통째로 비어 있었다. 두 기능 다 "동작하는 걸 본 적이
없는" 상태. 야외·Mac 이 필요한 항목은 놔두고 **에뮬레이터만으로 끝낼 수 있는
것**부터 털기로 했다.

## 1. 검증 환경에서만 3시간 가까이 썼다

앱 코드를 건드리기 전에 환경이 세 번 발목을 잡았다. 다음에 또 겪지 않도록
원인과 처방을 남긴다.

### ① 에뮬레이터가 9/15 상태로 얼어 있었다

부팅하자마자 달리기 화면에 `00:10`짜리 러닝이 떠 있고 ANR 이 났다. 로그의
이 줄이 정체를 알려줬다:

```
Last (wallTime=2026-09-15T04:19:15Z ...) and current (wallTime=2026-09-18T14:21 ...)
```

퀵부트 스냅샷이 **마지막 작업 세션(9/15 새벽) RAM 을 그대로 복원**한 것이다.
3일 묵은 상태라 시스템 서비스들이 뒤엉켜 있었다.

→ `emulator -avd Pixel_9_API35 -no-snapshot-load` 로 콜드 부팅. `-wipe-data`
가 **아니므로 앱 데이터는 보존된다** — 마이그레이션 검증 대상이 날아가면 안
되니 이 구분이 중요했다.

### ② ⭐ 진짜 원인은 RAM 2GB 였다

콜드 부팅 후에도 `Process system isn't responding`, `System UI isn't responding`
이 계속 났다. **앱이 아니라 시스템이** ANR 을 내는 게 이상해서 로그를 팠더니:

```
lowmemorykiller: Kill 'com.google.android.apps.restore' ... reason: low watermark is breached
```

`hw.ramSize=2G` 인데 `MemFree` 가 96MB. 디버그 APK 가 221MB(JIT·kernel_blob
포함)로 무거운 데다 구글 서비스까지 겹쳐 메모리가 바닥났던 것.

→ `~/.android/avd/Pixel_9_API35.avd/config.ini` 의 `hw.ramSize` 를 **2G → 4096**
으로 올렸다(원본은 `config.ini.bak-20260918` 로 백업). `MemAvailable` 이
681MB → 2.0GB 가 되면서 ANR 이 완전히 사라졌다.

> **ANR 이 앱 이름으로 떠도 앱 탓이라고 단정하면 안 된다.** 이번엔 세 번 중
> 두 번이 시스템 프로세스였고, 진짜 원인은 메모리였다.

### ③ 빌드와 에뮬레이터를 동시에 돌리지 말 것

첫 ANR 은 gradle 빌드(476초)가 CPU 를 잡고 있는 동안 났다. 빌드 후
`./gradlew --stop` 으로 데몬 2개를 내리니 호스트 메모리도 돌아왔다.

### 이번에 쓴 명령

```bash
emulator -avd Pixel_9_API35 -no-snapshot-load   # 콜드 부팅(데이터 보존)
adb emu geo fix <경도> <위도>                    # 모의 좌표 주입
adb shell am force-stop com.runearth.run_earth   # 강제 종료
adb exec-out run-as com.runearth.run_earth \
    cat /data/data/com.runearth.run_earth/app_flutter/run_earth.sqlite > local.sqlite
```

> 9/14 노트 §5 의 `com.example.run_earth` 는 **오기**다. 실제 패키지는
> `com.runearth.run_earth`. 그대로 실행했으면 force-stop 이 조용히 아무것도
> 하지 않아, 검증에 성공했다고 착각할 뻔했다.

## 2. 뜻밖의 수확 — 마이그레이션을 실데이터로 검증했다

에뮬레이터에 깔려 있던 앱이 `lastUpdateTime=2026-09-13`, 즉 **스냅샷 커밋
이전 빌드**였다. 덕분에 새 APK 를 덮어씌우는 것만으로 **drift v3→v4 마이그레이션이
실제 사용자 데이터 위에서 처음 도는** 상황이 그대로 재현됐다. 계획에 없던
검증인데, 여기서 깨졌다면 기존 사용자 기록이 날아가는 문제였다.

| 확인 | 결과 |
|---|---|
| `PRAGMA user_version` | **4** |
| `active_runs` 테이블 생성 | ✅ (0행) |
| 기존 `runs` 보존 | ✅ **3건 전부** — 경로·커버이미지·`synced_at` 무손실 |
| 홈 화면 반영 | ✅ 총 거리 0.3km / 총 횟수 3회 / 여정 서울→인천 26.8km 남음 |

## 3. ✅ 스냅샷·복원은 설계대로 동작한다

모의 좌표 10개를 30m 간격(약 3초마다)으로 주입하며 러닝을 돌렸다.

**추적 중 스냅샷** — `active_runs` 를 직접 열어 확인:

```
id=0  경과=88s  거리=0.26910km  일시정지=0  좌표=10개
started_at 23:41:43 → updated_at 23:43:13   (90초간 갱신)
```

주입한 좌표 10개 = 세그먼트 9개 × 30m = **270m** 인데 기록은 **269m**.
오차 1m. 거리 계산이 정확하다.

**강제 종료 → 재실행**:

- 묻지 않고 **조용히** 달리기 탭으로 복귀 ✅ (확인 팝업 없음 — 7장대로)
- 거리 `0.27km`, 경로 폴리라인이 지도 위에 **그대로** 복원 ✅
- 복원 직후 첫 좌표가 거리에 더해지지 않음 ✅ (`_skipNextSegment` 동작)

**STOP 저장 순서** — 7장이 못 박아둔 "저장 성공 뒤에 스냅샷 삭제":

- `runs` 4건 저장(기존 3 + 신규 1) → `active_runs` **0행** ✅
- 신규 기록: `run_1789742721744799 | 09.18 | 0.270km | 03:23 | 좌표 11개`
- 경로 이미지 렌더 정상, `synced_at=None` 으로 동기화 큐 적재 ✅

> 8장 완료 조건 "러닝 중 앱이 강제 종료돼도 다시 켰을 때 이어서 뛸 수 있다" 는
> **에뮬레이터 범위에서 충족**됐다. 다만 아래 §4-① 때문에 실기기 조건은 아직이다.

## 4. 🔴 결함 2건을 찾았다

### ① `POST_NOTIFICATIONS` 미선언 — 포그라운드 알림이 뜨지 않는다

`dumpsys notification` 통계:

```
numEnqueuedByApp=1   ← 앱이 알림을 요청했고
numPostedByApp=0     ← 뜬 건 0건
numBlocked=1         ← 차단됨
numForegroundService=0
```

매니페스트에 `FOREGROUND_SERVICE_LOCATION` 은 챙겼는데
**`POST_NOTIFICATIONS` 가 없다.** 이 앱은 `targetSdkVersion=36` 이라
Android 13(API 33)+ 의 런타임 알림 권한이 필수다.

**정확히 쓰자.** 9/14 노트 §5 체크리스트 1번은 "알림이 안 뜨면 서비스 시작
실패"라고 적었는데, 실측은 다르다:

```
startForegroundCount=1        ← 서비스는 떴다
ServiceRecord{... com.baseflow.geolocator.GeolocatorLocationService}
```

**서비스는 시작됐고 알림만 차단된** 상태다. 그래도 고쳐야 하는 이유 둘:

1. 사용자가 추적 중인지 알 수 없다.
2. 9/14 §5 에서 우려한 **삼성 앱 절전은 보이지 않는 FGS 를 훨씬 쉽게 죽인다.**
   포그라운드 서비스를 도입한 목적 자체가 무력화된다.

→ **이걸 고치기 전에는 야외 실기기 테스트를 나가도 의미가 없다.**

### ② `restoreIfAny()` 의 3초 타임아웃이 콜드 스타트에서 터진다

OS 콜드 부팅 후 첫 실행에서:

```
[splash] 러닝 복원 실패 — 홈으로 진행: TimeoutException after 0:00:03.000000
```

웜 스타트 3회는 전부 통과했으니 **콜드 스타트 전용 증상**이다(DB 파일이 페이지
캐시에 없고 시스템도 바쁜 상태).

이번엔 복원할 스냅샷이 없어 결과적으로 무사했지만, **있었다면 그대로 건너뛰고
진행 중 러닝을 잃는다.** 9/14 노트의 "행 하나 읽는 일이라 3초면 넉넉하다" 는
가정이 깨졌고, 하필 **기기 재부팅 직후 첫 실행**이 정확히 이 조건이다.

> 이 타임아웃은 9/14에 위젯 테스트의 무한 대기를 막으려고 넣은 것이다. 테스트를
> 살리려던 장치가 실기 동작을 깎아먹은 셈 — 스플래시를 막지 않으면서 복원은
> 놓치지 않는 쪽으로 다시 설계해야 한다(예: 라우팅을 먼저 하고 복원은 뒤따르게).

## 5. 🟡 문서에 없어서 남겨두는 것 (가정하지 않았다)

- **복원 시 경과 시간 정의.** 앱이 죽어 있던 구간이 시간에서 **빠진다**
  (실측 표시 `02:09` vs 실제 경과 181초). `run-flow.md` 7장은 **거리**만
  정의하고("복원 직후 첫 좌표는 거리에 더하지 않는다") 시간은 언급이 없다.
  죽은 구간을 러닝 시간에 포함할지 뺄지 **결정 필요**.
- **0km 기록 정책의 실물 증거.** 실수로 시작한 22초·0.00km 러닝이
  `run_1789742870933776` 으로 **그대로 저장됐다.** 9/13 §3-4 · `records.md`
  4장 충돌 항목이 실제로 어떻게 새는지 보여주는 사례다.
