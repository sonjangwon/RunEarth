## 0. 시작 시점 상태

9/13 노트 §4의 우선순위는 ①기록 유실 방지 ②기록 상세 화면 ③백그라운드 추적

## 1. ⭐ 우선순위를 뒤집었다 (①↔③)

9/13에는 "스냅샷 먼저, 포그라운드 서비스 나중"으로 적어뒀는데 이번에 뒤집었다.
근거 두 가지:

**스냅샷은 손실을 막는 게 아니라 줄인다.** 프로세스가 죽어 있는 동안 GPS도
같이 꺼져 있다. 복원해봐야 **경로에 구멍이 뚫린 기록**이 남고, 10분 끊겼으면
그 10분은 어디서도 못 되찾는다. 포그라운드 서비스는 애초에 안 죽게 만드는
것이라 성격이 다르다.

**더 큰 결함이 가려져 있었다.** 지금 앱은 화면을 켜고 있어야만 동작한다.
9/13 야외 테스트가 성공한 것도 **화면을 계속 켜두고 뛰었기 때문**이다.
주머니에 넣으면 거리가 안 쌓이는 앱은 러닝앱으로 쓸 수 없다. "진행 중 러닝
유실"보다 이쪽이 크다.

정리하면 **스냅샷은 포그라운드 서비스의 안전망이지 대체재가 아니다.**
안전망보다 본체가 먼저다. 순서만 바꾸고 스냅샷은 그대로 뒤에 붙였다(둘 다
이 세션에서 끝냈다).

## 2. 포그라운드 서비스 — 커밋 `6ad72b3`

`run_tracker.dart` 가 평범한 `LocationSettings` 를 쓰고 있어 Android 8+ 의
백그라운드 위치 제한에 걸렸다. `run-flow.md` 6장 '백그라운드 위치 추적' 을
구현한다.

- `_locationSettings()` 로 플랫폼 분기. Android 는 `AndroidSettings` +
  `foregroundNotificationConfig`(제목 `Run Earth` / 본문 `러닝을 기록하는
  중이에요`, 웨이크락 ON, `setOngoing` 으로 지울 수 없는 알림).
- **`intervalDuration: 3초` 를 명시했다.** 지금까지는 거리 필터 5m 만 있고
  간격은 OS 재량이었다. 9/13 실측(3.1초)으로 검증된 값을 설정으로 고정한 것.
- iOS 는 `AppleSettings` + `activityType: fitness`,
  `pauseLocationUpdatesAutomatically: false`(신호등 대기 중 멈추면 곤란).
- 매니페스트: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, `WAKE_LOCK`.
  Flutter 3.44.6 의 기본 `targetSdk` 가 34 이상이라 `_LOCATION` 은 **필수** —
  없으면 서비스 시작 시 즉시 크래시한다.
- `Info.plist`: `UIBackgroundModes: location`. Mac 이 없어 **빌드 검증 불가**.

### `ACCESS_BACKGROUND_LOCATION` 은 일부러 뺐다

`run-flow.md` 6장은 이 권한이 필요하다고 적고 있었으나 **포그라운드 서비스
방식에서는 불필요하다.** 앱이 화면에 떠 있는 상태에서 서비스를 시작하기
때문이다. 넣으면 사용자에게 '항상 허용' 승격을 따로 요구하게 되어 이탈만
늘어난다. 문서를 정정하되 **실기기 검증 후 확정**으로 표시해 뒀다.

### ⚠️ geolocator 방식의 한계 (중요)

`AndroidSettings` 의 주석에 이렇게 적혀 있다:

> 이 포그라운드 알림은 서비스를 백그라운드로 돌리는 게 아니라, 액티비티의
> 우선순위를 높여 앱 전환 시 Android 가 죽일 가능성을 낮출 뿐이다.
> **죽는 것을 막지는 못한다.**

즉 OS 에게 "죽이지 마세요"라고 **부탁**하는 것이지 강제가 아니다. 완전한
보장이 필요하면 별도 Flutter 엔진을 띄우는 서드파티 백그라운드 패키지가
필요하다. 새 패키지 도입은 **실측 결과를 보고 판단**하기로 했다.

이 한계 때문에 **뒤이은 스냅샷의 필요성이 어제 판단보다 커졌다.**

## 3. 진행 중 러닝 스냅샷 — 커밋 `8f779e0`

9/13 §3-1 의 최우선 항목. `run-flow.md` 7장의 `[미확정]` 을 확정한다.

- drift 스키마 **v4**: `ActiveRuns` 테이블(항상 0~1행, `id=0` 고정). 시작시각·
  경과시간·거리·경로·일시정지 여부를 담고 추적 중 **10초마다 덮어쓴다.**
- `restoreIfAny()` — 앱 시작 시 스냅샷이 있으면 **묻지 않고 조용히** 이어붙이고
  달리기 탭으로 보낸다. 스플래시에서 호출한다.
- 마지막 갱신이 **6시간**보다 오래됐으면 이어 뛰지 않고 그대로 기록으로 확정한다.

### 저장 방식: 10초 스냅샷 vs 좌표 append

45B/좌표 · 147좌표/km(9/13 실측 기준)로 계산해 비교했다.

| | 10초 스냅샷 | 좌표 append |
|---|---|---|
| 최대 손실 | 10초 (약 30m) | **0** |
| 총 쓰기 — 2.6km/20분 | ~1MB | ~50KB |
| 총 쓰기 — 10km/60분 | ~12MB | ~190KB |
| 총 쓰기 — 풀코스/4시간 | ~200MB | ~750KB |
| 새 테이블 | 1개 | **2개** |

**스냅샷을 택했다.** 표만 보면 append 압승이지만 절대값을 보면 둘 다 문제가
안 된다 — 풀코스 200MB 는 4시간에 걸쳐 쓰는 것이라 초당 14KB 고, 대부분의
사용자는 10km 이하(12MB)다. 30m 손실도 10km 기록에서 0.3% 이고 **앱이 죽었을
때만** 발생한다(정상 종료 시 0).

게다가 **append 는 테이블이 2개 필요하다.** 좌표만 쌓아서는 복원이 안 되는데,
특히 거리를 좌표에서 재계산하면 **틀린다** — 일시정지 구간을 거리에서 빼는
로직이 있어서 단순히 좌표를 이으면 일시정지 중 이동분이 더해진다. 결국 세션
메타를 따로 덮어써야 해서 append 의 이점이 반감된다.

남는 차이는 구현 복잡도 하나뿐이고, **유실을 막으려는 기능이 복잡해서 버그가
나면 본말전도다.**

> 나중에 풀코스 쓰기량이 정말 걸리면, 거리가 길어질수록 스냅샷 간격을 늘리는
> 식으로 **방식을 안 바꾸고도** 줄일 수 있다.

### 주의한 순서 두 가지

**① 스냅샷 삭제는 `upsertRun` 성공 뒤에.** STOP 을 누르고 DB 에 쓰기 직전에
죽는 찰나가 있는데, 순서를 반대로 하면 바로 그 순간에 기록이 사라진다.

**② 복원 직후 첫 좌표는 거리에 더하지 않는다**(`_skipNextSegment`). 앱이 죽어
있는 동안 이동했다면 마지막 좌표와 새 좌표가 크게 벌어지는데, 그대로 더하면
**추적하지도 못한 구간**이 거리에 잡혀 페이스만 왜곡된다. 일시정지 복귀와
같은 처리다.

### 만료 스냅샷은 커버 이미지 없이 저장한다

이미지 렌더(`route_image_renderer.dart`)는 화면 계층 코드라 데이터 계층에서
부를 수 없다. 어차피 `route` 좌표만 있으면 어디서든 다시 그릴 수 있다
(2026-09-11 결정, 9/13 실측으로 확인됨).

## 4. ⭐ 위젯 테스트가 9/13 버그를 재현해냈다

`flutter analyze` 는 통과했는데 `flutter test` 가 깨졌다. `pumpAndSettle
timed out`. `git stash` 로 HEAD 와 비교해 **이번 변경이 원인**임을 확인했다.

원인: 스플래시에서 복원을 `await` 하게 만들었는데, **DB 응답이 오지 않으면
그 자리에서 영원히 멈춘다.** 테스트 환경에는 `path_provider` 구현이 없어
DB future 가 영영 완료되지 않았다.

**9/13 §1-D 와 똑같은 뿌리다.** 스플래시는 사용자가 빠져나올 수단이 없는
화면이라 스피너인 채로 갇힌다. 그때 넣어둔 `try/catch` 는 **예외만** 잡지,
응답이 안 오는 경우는 못 막는다.

→ `restoreIfAny()` 호출에 **3초 타임아웃**. 행 하나 읽는 일이라 넉넉하고,
넘어가면 그냥 홈으로 보낸다.

> 실기기에서는 DB 가 정상이라 **평생 안 드러났을 버그**다. 위젯 테스트 하나가
> 잡아냈다. `flutter analyze` 만으로는 부족하다는 근거로 남겨둔다.

## 5. 검증 대기 (오늘 아무것도 실행해보지 못했다)

| 항목 | 구현 | 검증 |
|---|---|---|
| 포그라운드 서비스 | ✅ | ⬜ **야외 필요** — 화면 끄고 5~10분 |
| 진행 중 러닝 스냅샷 | ✅ | ⬜ 에뮬레이터로 가능 |
| iOS 백그라운드 설정 | ✅ | ⬜ **Mac 필요** |

스냅샷은 에뮬레이터만으로 검증된다 — 야외에서 우연히 죽기를 기다리는 것보다
확실하다:

```bash
adb shell am force-stop com.example.run_earth   # 러닝 중에 강제 종료
# 앱 재실행 → 달리기 탭에 그대로 이어지는지 확인
```

포그라운드 서비스 확인 순서(빌드 후):

1. START 시 상단 알림바에 `Run Earth` 가 뜨는가 (안 뜨면 서비스 시작 실패 —
   나가서 뛸 필요도 없다)
2. 화면 끄고 주머니에 넣고 5~10분 뒤 거리가 쌓여 있는가
3. 알림 아이콘이 흰 사각형으로 뭉개지는가 → 전용 단색 아이콘 제작 필요

> 테스트 기기가 **갤럭시 노트8**인 게 변수다. 삼성은 '앱 절전'이 공격적이라
> 포그라운드 서비스도 재우는 걸로 유명하다. 설정 → 배터리 → 백그라운드 사용
> 제한에서 Run Earth 를 빼고 테스트해야 정확하다.
