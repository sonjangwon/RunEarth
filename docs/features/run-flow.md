## 달리기 실행 로직 (Run Execution — 공통)

**최종 수정일**: 2026-08-15
**상태**: 🟢 핵심 로직 확정 · 일부 렌더링/복구 정책 미확정
**담당**: 기획/디자인 - OOO / 개발 - OOO
**적용 범위**: 일반 러닝 / 테마 러닝 / 온라인 마라톤 **공통** 트래킹·저장 로직.
코스 오버레이·완주 판정 등 러닝 타입별 차이는 `theme-running.md`,
`online-marathon.md`에서 별도로 다룬다.

### 1. 개요

기존 기능정의서에는 화면 상태 머신(idle/running/paused/stopped)만 정의돼
있고, 실제 구현에 필요한 백그라운드 추적, GPS 정밀도, 일시정지 시 동작,
대표 이미지 처리 로직이 빠져 있었다. 이번에 이 부분들을 확정한다.

### 2. 사용자 시나리오

- START 탭 → 러닝 시작. **앱이 백그라운드로 가도 GPS 추적이 계속된다**
- PAUSE 탭 → 거리·시간 누적 중단. **지도상 현재 위치 표시는 계속 갱신되지만,
  일시정지 중 이동한 구간은 경로 기록에 포함되지 않는다**
- RESUME 탭 → 누적 재개. 일시정지 중 이동으로 인해 경로 라인에 끊긴 구간이
  생길 수 있음(자연스러운 현상)
- STOP 탭 → 종료 결과 화면(RunDetailView) 진입
  - 사진 등록 안 함(기본값) → **실제 트래킹된 경로를 네온그린 라인으로 그린
    이미지**가 대표 이미지로 자동 생성/저장
  - 사진 등록함(선택, 1장만) → 등록한 사진이 대표 이미지
- 이후 "기록" 탭에서 해당 기록 상세 진입 시, **대표 이미지를 언제든 교체
  가능** (사진 ↔ 경로 이미지 자유 전환)

### 3. 화면 구성

**러닝 중 / 일시정지 중**
- 실시간 지도 + 진행 중인 실제 이동 경로 라인(네온그린, `#00E87A`)
- 상단 오버레이: 거리 / 페이스 / 경과 시간
- 일시정지 중에는 "일시정지됨" 뱃지 노출, 타이머 시각적으로 정지 표시

**종료 결과 (RunDetailView)**
- 대표 이미지 영역:
  - 사진 미등록 시: 자동 생성된 경로 렌더 이미지 — **실제 지도 배경 없이,
    네온그린 경로 라인만 심플한 어두운 단색 배경 위에 표시** (나이키 러닝
    앱 스타일의 지도+경로 합성이 아님)
  - 사진 등록 시: 등록 사진 풀블리드
- 대표 이미지 하단/오버레이: "사진 등록" 또는 "사진 변경" 버튼(선택 사항)
- km / 페이스 / 타임 / 칼로리 표시 (기존 정의 유지)

**기록 탭 상세 (해당 Run 재조회 시)**
- 대표 이미지 영역에 "대표 이미지 변경" 버튼 추가
- 탭 시 바텀시트: "사진으로 변경" / "경로 이미지로 변경" 2개 옵션

### 4. 컴포넌트 & 상태 정의

| 상태 | 위치 추적 | 거리/시간 누적 | 경로 기록 |
|---|---|---|---|
| running | ON | ON | ON |
| paused | ON (현재 위치 표시만 갱신) | OFF | OFF |
| stopped | OFF | — | — |

**대표 이미지 소스 결정**

| 조건 | 대표 이미지 |
|---|---|
| 사용자가 사진 등록함 | 등록 사진 |
| 사진 미등록(기본값) | 자동 생성 경로 이미지 (네온그린 라인) |
| 기록 탭에서 이후 변경 | 사용자가 선택한 쪽으로 교체 (양방향 전환 가능) |

### 5. 인터랙션 / 마이크로카피

  이미지가 돼요"
- 기록 탭 대표 이미지 변경 바텀시트: "사진으로 변경" / "경로 이미지로 변경"

### 6. 데이터 요구사항 (개발자 확인 필요 영역)

**백그라운드 위치 추적**
- iOS: "사용 중 허용"만으로는 백그라운드 추적이 안 됨 — Background Modes
  (Location updates) 설정 + 사실상 "항상 허용" 수준의 동작이 필요
- Android: Foreground Service 필요.
  ~~`ACCESS_BACKGROUND_LOCATION` 권한 필요~~ → **불필요 (2026-09-15 구현 시 정정)**.
  앱이 화면에 떠 있는 상태에서 서비스를 시작하므로 '항상 허용' 승격이 필요
  없고, 요구하면 이탈만 늘어난다. **실기기 검증 전이므로 검증 후 확정.**
- `global-states.md`에서 정의한 로그인 직후 권한 요청은 **"사용 중 허용"**
  수준이므로, 러닝 시작 시점에 **추가 승격**이 필요할 수 있음

**알림 권한 (`POST_NOTIFICATIONS`)** — 🟢 확정 (2026-09-19)
- Android 13(API 33)+ 는 알림이 런타임 권한이다. 이 앱은 `targetSdkVersion=36`
  이라 해당된다. 포그라운드 서비스 알림도 예외가 아니다.
- **왜 필요한가**: ① 사용자가 추적 중인지 알 수 있는 유일한 표시이고,
  ② 제조사 절전(삼성 등)이 보이지 않는 FGS 를 훨씬 쉽게 죽인다 —
  포그라운드 서비스를 도입한 목적 자체가 무력화된다.
- **정정**: 권한이 없어도 **서비스는 시작된다.** 알림만 조용히 차단된다
  (2026-09-18 실측: `startForegroundCount=1`, `numPostedByApp=0`,
  `numBlocked=1`). "알림이 안 뜨면 서비스 시작 실패"는 틀린 설명이었다.
- **요청 시점**: 러닝 시작(START) 직전. 앱 최초 실행이 아니다 — 맥락이 있을 때
  물어야 승인률이 높다.
- **사전 안내 후 요청**: 시스템 팝업 전에 "러닝 중 상단바에 기록 상태를
  표시합니다"를 먼저 보여준다. 안드로이드는 **두 번 거부당하면 영구 거부**가
  돼 앱에서 다시 물어볼 수 없으므로, 맥락 없는 팝업은 비용이 크다.
- **거부해도 러닝을 막지 않는다.** 알림 없이도 추적 자체는 되므로 차단은
  과하다. 대신 "알림을 허용하지 않으면 화면을 끈 사이 기록이 끊길 수 있어요"
  경고를 띄우고 진행한다. (위치 권한은 거부 시 **시작을 막는다** — 이쪽과 다르다.)
- iOS 는 대상이 아니다. 포그라운드 서비스 개념이 없고 백그라운드 위치는
  Background Modes 로 처리하므로 알림 권한이 추적 지속성에 영향을 주지 않는다.
- **[미검증]** 제조사 절전이 실제로 FGS 를 죽이는지는 야외 실기기 테스트에서
  확인해야 한다. 알림을 먼저 정상화해야 그 테스트 결과를 해석할 수 있다.
- → **[제안 기본값]** 별도 커스텀 승격 UI를 만들지 않고, OS가 자동으로
  띄우는 표준 승격 다이얼로그(예: iOS가 자체적으로 "계속 위치를 사용
  하시겠어요?"를 띄우는 경우)에 맡긴다. **[미확정]** 실기기 테스트 후
  이 기본값으로 충분한지, 별도 안내 화면이 필요한지 판단 필요

**GPS 샘플링**
- **[제안값]** 3초 간격 + 최소 이동거리 5m 필터 조합 (정지 상태에서 GPS
  노이즈로 거리가 계속 증가하는 현상 방지). 일반적인 러닝 앱 수준의
  절충안. 실측 테스트 후 조정 가능
  - 2026-09-13 야외 실측(2.61km/383점 = 3.1초·6.8m)으로 두 값 검증됨.
- 🟢 **5m 를 거는 위치를 옮겼다 (2026-09-19 확정).** 값 자체는 그대로다.
  - 위치 스트림의 `distanceFilter` 는 **0**. 거기서 거르면 5m 를 움직이기
    전까지 **위치가 아예 들어오지 않아** 지도가 폴백 좌표에 멈추고
    'GPS 신호를 기다리는 중' 배지도 안 사라진다. 출발선에 서 있으면 신호가
    멀쩡한데도 대기 중으로 보였다.
  - 최소 이동거리 5m 검사는 **거리·경로를 누적할 때만** 한다. 정지 중 노이즈
    방어는 그대로 유지된다.
  - 현재 위치(지도·배지용)는 3초마다 **항상** 갱신한다.
- 🟢 **GPS 는 카운트다운 시작과 함께 켠다 (2026-09-19 확정).** 예전에는
  카운트다운이 끝난 뒤에야 스트림을 열어 3초를 버렸다. 이 구간 좌표는 phase 가
  running 이 아니라 거리에 누적되지 않는다.
- 🔴 **GPS 튐 거르기 — 속도 상한 6.0 m/s (2026-09-23 야외 검증으로 추가).**
  이전 좌표 대비 속도가 이보다 빠르면 **그 좌표를 통째로 버린다.** 앵커는
  그대로 둬서 다음 좌표가 제자리를 찾으면 이어진다.
  - 6.0 m/s 는 `2'47"/km` — 마라톤 세계기록 페이스(약 5.7 m/s)보다도 빠르다.
  - 좌표가 **30초 넘게 끊겼다 돌아오면 속도 검사를 건너뛴다.** 그때는 멀리
    떨어져 있는 게 정상이고, 속도로 재면 무조건 튐으로 보여 앵커가 영영
    안 움직인다. RESUME 과 같이 **앵커로만 쓰고 거리에 더하지 않는다.**
  - '버리기' 와 '거리만 상한까지 깎기' 둘 다 검토했고 **버리기로 정했다**
    (2026-09-23 사용자 결정).
- 🔴 **배터리 최적화 제외를 요청한다 (2026-09-23 추가).** 달리기 시작 때
  사전 안내 → 시스템 다이얼로그. **거부해도 러닝은 막지 않는다**(알림 권한과
  같은 원칙). 매니페스트 권한은 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.

#### 🟢 2026-09-26 실측 검증 — 거리는 맞고, **경로 모양이 틀렸다**

같은 폰(갤럭시 노트8)에서 우리 앱과 아이폰의 다른 러닝 앱을 **동시에** 켜고
2.4km 를 뛴 데이터로 확인했다. 좌표 167개, 전부 정확도(`a`)·기기속도(`s`) 수집.

| | 거리 | 시간 |
|---|---|---|
| 우리 앱 (노트8) | **2.41 km** | 20:01 |
| 다른 앱 (아이폰, 동시) | **2.39 km** | 21:04 |

**거리는 0.84% 차이 — 사실상 일치한다.**

##### 🔴 정확도 필터는 거리에 넣으면 안 된다

임계값별로 앱 알고리즘을 그대로 재현해 돌린 결과다. 이 폰은 정확도 중앙값이
20m 라, 거르면 **실제로 지나간 경로가 통째로 사라진다.**

| 정확도 임계값 | 버린 좌표 | 거리 | 실측(2.39) 대비 |
|---|---|---|---|
| **없음 (현재)** | 0개 | 2.56 km | +7% |
| 70m | 7개 | 2.10 km | -12% |
| 50m | 18개 | 1.83 km | **-23%** |
| 30m | 34개 | 1.46 km | -39% |
| 10m | 111개 | 0.37 km | -85% |

OpenTracks 가 50m 를 쓴다고 따라가면 **23% 짧아진다.** 기기·환경에 따라
분포가 달라서, 남의 임계값을 그대로 가져오면 안 된다는 뜻이다.

##### 🔴 그런데 경로 모양은 망가져 있다

지도에서 점프로 보이는 100m 초과 구간이 **4개, 합계 924m** 였다.

| 구간 | 앵커 정확도 → 다음 | 거리 처리 |
|---|---|---|
| 457m / 31초 | **533m** → 9m | stale 로 거리엔 안 더함 |
| 199m / 32초 | 56m → 9m | stale 로 거리엔 안 더함 |
| 138m / 24초 | 70m → 90m | **거리에 더해짐** |
| 130m / 24초 | 78m → 83m | **거리에 더해짐** |

- **튀는 것은 새 좌표가 아니라 앵커(이전 좌표)다.** 큰 점프 2건 모두 앵커의
  정확도가 나빴다(533m·56m). 지금 속도 필터는 새 좌표를 버리고 나쁜 앵커를
  남기는데, 오늘은 두 건 다 30초를 넘겨 `stale` 로 빠져서 문제가 안 됐다.
- **거리에서 뺀 구간도 지도에는 선으로 그려진다.** 좌표를 경로 배열에는
  남기기 때문이다. 457m 짜리 직선이 화면에 보인다.
- 정확도 50m 초과 좌표 **18개(11%)** 가 전부 경로에 남아 북쪽 구간이
  지그재그가 된다.

##### 🟢 결론 — 거리와 경로를 분리한다 (2026-09-26)

**거리 계산에는 정확도 필터를 넣지 않는다.** 위 표가 근거다.
**경로 렌더(지도·대표 이미지)에는 넣는다.** 지금은 사용자가 보는 그림이
실제로 뛴 길과 다르다. 경로 이미지는 기록 카드의 대표 이미지로도 쓰인다.

할 일 3건 — `feature-backlog.md` 에도 올려뒀다:
1. **경로 렌더에 정확도 필터** (거리 로직은 건드리지 않는다)
2. **`stale` 구간은 선을 끊는다** — 거리에 안 더하는 구간이면 선도 잇지 않는다
3. **`stale` 임계값 30초 재검토** — 24초짜리 점프 2건(268m)이 그 아래라
   거리에 그대로 들어갔다

- **`stale` 로직은 설계대로 동작하고 있었다.** 9/26 경로를 그냥 합산하면
  3.236km 인데 저장된 거리는 2.41km — **추적하지 못한 825m 를 정확히
  빼냈다.** 다른 앱과 거리가 맞았던 게 우연이 아니라는 근거다.
- **경로 렌더 3건의 성격이 바뀐다.** 절전 OFF 데이터에는 거를 좌표가
  **0개**라, 지금 정확도 필터를 넣어도 검증할 대상이 없다. 3건은
  "절전 모드 상황 방어"로 성격을 좁히고 우선순위를 내린다.
  **실질적인 해결책은 START 전 절전 모드 안내**다(7 엣지 케이스).

> ⚠️ **절대 거리 정확도는 아직 판정되지 않았다.** 0.72km 짜리라 기준 코스도
> 비교 앱도 없었다. 여기서 확인된 것은 **좌표 품질과 경로 모양**이다.
> 거리를 아는 코스에서의 실측은 그대로 남아 있다.

#### 왜 이 둘이 필요했나 (2026-09-23 야외 검증)

갤럭시 노트8 릴리즈 빌드로 실제 야간 러닝 4건을 기록해 좌표를 뜯어봤다.

**① 화면을 끄면 안드로이드가 위치 갱신을 늦춘다.** 3초를 요청해도 실제로는
**8~11초** 간격으로 왔다(274구간 중 113개가 정확히 8초). 앱이 폰의 절전 예외
목록에 없어서 제한 대상이었다. 시간대별로 보면 분명하다:

| 경과 | 좌표 간격 | 말이 안 되는 구간 |
|---|---|---|
| 0~4분(화면 켬) | 5~6초 | **0개** |
| 8~16분 | 9~11.6초 | 2개 |
| 20~30분 | 7~8초 | 16개(1,398m) |

**② 간격이 벌어지면 GPS 흔들림이 한 번에 뭉쳐 들어온다.** 5.14km 로 찍힌
기록에서 **25개 구간이 사람이 못 내는 속도**였고(최악: 7초에 126m = 시속 65km),
그 거리 합이 **1,785m — 총 거리의 35%** 였다.

**③ 간격만이 원인은 아니다.** 간격이 5초로 촘촘했던 1.17km 기록에도 시속
53km 구간이 있었다. 밤에 건물·나무 근처에서 GPS 자체가 부정확했다. 그래서
절전 제외(①)만으로는 부족하고 속도 필터(②)가 함께 필요하다.

> ⚠️ **아직 과다 계상이 남아 있다.** 사용자가 "실제로는 1km 가 안 됐다"고 한
> 기록이 필터를 거쳐도 1.05km 다. 추정치 하나에 맞춰 더 조이면 과교정
> 위험이 있어, **다음 야외 검증(거리를 아는 코스)에서 조정한다.**
> 조일 곳은 최소 이동거리(지금 5m)와 속도 상한(지금 6.0 m/s) 두 개다.

- 🟢 **캐시된 마지막 위치로 지도를 즉시 채운다 (2026-09-19 확정).** 첫 fix 는
  수 초~수십 초 걸리고 그동안 지도가 폴백(서울시청)에 머문다.
  **단 캐시 위치는 지도 카메라 전용이다** — 몇 시간 전 수 km 떨어진 값일 수
  있어 경로에 넣으면 첫 실제 fix 까지의 직선거리가 통째로 잡힌다.

**경로 렌더 이미지**
- GPS 좌표 배열(polyline)을 네온그린(`#00E87A`) 라인으로 렌더링, 배경은
  실제 지도 타일 없이 단색/그리드 정도만
- → **[미확정]** 렌더링을 클라이언트(앱 내 캔버스/SVG)에서 할지, 서버에서
  이미지로 생성해 URL로 내려줄지 — 서버 렌더링이 여러 화면(기록 리스트
  썸네일 등)에서 일관성 있게 재사용하기 유리함

**데이터 모델 확장**

```typescript
type Run = {
  // ...기존 필드 (date, day, km, pace, dur, kcal, type, year, month)
  coverImageType: "photo" | "route";  // 신규
  coverImageUrl: string;              // 신규 — photo면 업로드 사진, route면 자동 생성 이미지
  route: { lat: number; lng: number; t?: number }[];  // 실제 추적된 좌표
};
```

- 대표 이미지 교체 API 필요 (`coverImageType`, `coverImageUrl` 갱신)

#### 6-1. 좌표의 시각 `t` (2026-09-21 확정)

`route` 의 각 좌표에 **그 지점을 지난 시각**을 함께 적는다.
UTC epoch 밀리초, 위치 fix 시각(`Position.timestamp`)을 쓴다 — 기기 시계가
아니라 fix 시각이어야 좌표가 화면까지 오는 지연이 구간 페이스에 안 섞인다.

**왜 지금 넣는가**: 구간 페이스(KM splits)를 내려면 좌표마다 시각이 필요한데,
**달리는 그 순간에 적어두지 않으면 나중에 복원할 방법이 없다.** 화면(splits 표)은
나중에 만들어도 되지만 적재는 미룰 수 없어 먼저 넣는다.

**선택 필드인 이유**: 같은 좌표 타입을 `theme-running.md` 의 `courseRoute`
(사전 정의 코스)가 함께 쓴다. 코스 좌표는 지도에 그릴 선일 뿐이라 시각이
성립하지 않으므로 비워 둔다. 러닝 전용 타입을 따로 파는 대신 선택 필드로 둔 건,
경로를 그리는 코드가 여러 화면에 흩어져 있어 타입을 나누면 그 코드를 전부
고쳐야 하기 때문이다(2026-09-21 사용자 결정).

**저장**: 경로는 DB 칼럼 하나에 JSON 문자열로 통째 들어간다. 칸이 느는 게
아니라 그 문자열 안에 키가 하나 붙을 뿐이라 **스키마 변경·데이터 이전이 없다.**
`t` 가 없는 예전 기록도 그대로 읽힌다.

`t` 만으로는 부족해서 **`e`(달린 시간)도 함께 적는다** — 아래 6-2 참조.

#### 6-2. 구간별 페이스 (KM splits) — 2026-09-21 확정

`route` 좌표에서 **1km 단위**로 잘라 구간 페이스를 낸다.

```typescript
type Run = {
  route: { lat: number; lng: number; t?: number; e?: number;
           a?: number; s?: number }[];  // a·s 는 6-3
};
```

| 필드 | 뜻 | 쓰임 |
|---|---|---|
| `t` | 벽시계 시각(UTC epoch ms) | 서버 GPS 재검증·웨어러블 병합 |
| `e` | **달린 시간**(시작부터 누적 ms, **일시정지 제외**) | **구간 페이스 계산** |

**왜 `e` 가 따로 필요한가**: `t` 는 벽시계라 쉰 시간이 그대로 들어 있다.
2km 지점에서 5분 쉬면 그 구간만 페이스가 `11'20"`(실제 `6'20"`)로 튀고,
화면에 뜨는 총 시간(일시정지 제외)과도 어긋난다. 거리 쪽은 이미
`_skipNextSegment` 로 일시정지 구간을 빼고 있어 시간만 맞추면 된다.

**계산 규칙**

- 구간은 **1km 마다** 자른다. 마지막 자투리는 **실제 총거리로 라벨**(예: `2.89`)
- 자투리 구간의 페이스는 **1km 환산** — 그래야 온전한 구간과 나란히 비교된다
- 1km 경계는 좌표 사이에 걸리므로 **선형 보간**한다. 경계를 넘은 좌표의
  시간을 그대로 쓰면 구간이 실제보다 길어지고 그 오차가 뒤로 계속 밀린다
- 한 번에 여러 km 경계를 넘는 경우(신호가 끊겼다 돌아옴)도 처리한다

**표시 규칙(Figma)**

- 한 줄 = `{km} km` · 막대 · `{페이스}`. 막대는 **빠를수록 길다**
- 막대 길이는 그 기록 안에서 가장 빠른 구간(=꽉 참)과 가장 느린 구간(=10%)
  사이의 상대값. 구간이 하나뿐이거나 전부 같은 페이스면 다 꽉 채운다
- **좌표에 시간이 없는 기록(2026-09-21 이전)은 섹션째 그리지 않는다** —
  빈 카드를 남기면 고장난 것처럼 보인다

**코드 정본**: `features/run/data/km_splits.dart` (`computeKmSplits`,
`splitBarRatio`). 테스트는 `test/km_splits_test.dart`.

#### 6-3. GPS 품질 값 `a` · `s` — 2026-09-25 확정 (적재만)

| 필드 | 뜻 | 단위 |
|---|---|---|
| `a` | GPS 정확도 — 기기가 알려주는 "이 반경 안쪽" | 미터(반올림 정수) |
| `s` | **기기가 측정한 속도** — 도플러로 직접 잰 값 | cm/s(정수) |

**지금은 쌓기만 하고 아무것도 거르지 않는다.** 2026-09-23 야외 검증에서 거리가
35% 부풀었고 속도 상한(6.0 m/s)으로 한 겹 막았지만 과다 계상이 남았다. 정확도로
거르는 게 더 정석인데 **이 값을 저장하지 않아 임계값을 정할 근거가 없었다.**
거리를 아는 코스에서 한 번 뛰면 "20m 넘는 좌표를 버렸으면 거리가 얼마였을까"를
실제로 계산할 수 있다 — 그 재료를 먼저 쌓는다.

**왜 `s` 도 같이 넣는가**: 지금 튐 필터는 두 좌표의 **거리÷시간**으로 속도를
낸다. 앞 좌표와 뒤 좌표의 위치 오차가 둘 다 섞여 들어오는 값이다. `s` 는 GPS 가
도플러로 직접 잰 것이라 위치보다 정확하다. 한 번 나가서 두 방법을 다 비교해
보려면 둘 다 필요하다.

**기기가 값을 못 준 경우는 `null` 이다. `0` 이 아니다.** geolocator 는
`hasAccuracy`/`hasSpeed` 가 false 면 자리를 `0.0` 으로 채워 보낸다. 그걸 그대로
적으면 '오차 0m = 완벽한 좌표'로 읽혀 나중에 필터가 거꾸로 돈다.

**외부 사례의 임계값** (2026-09-25 조사)

| 사례 | 임계값 |
|---|---|
| OpenTracks (오픈소스 트래커) | 기본 **50m** 초과 버림 (선택 10/20/30/50/100…) |
| Mizutori 샘플 (러닝 전용) | **10m** |
| Avenza Maps | 32m |

거리를 재는 용도는 **10~30m** 쪽이다. 참고로 OpenTracks 의 최소 이동거리 기본값은
**10m**(우리는 5m)이고, 점 사이가 **200m** 를 넘으면 구간을 끊어 거리에 더하지
않는다(우리는 30초 시간 기준). Strava 공식 문서도 "지그재그가 직선으로 이어져
거리가 부푼다"고 인정하며, 불량 GPS 가 임계값을 넘으면 기기 거리와 섞어 재계산한다.
**완벽한 한 방은 없고 겹겹이 막는 게 정석이다.**

**진단 로그**: 속도 상한에 걸려 버린 좌표는 경로에 남지 않으므로 `debugPrint` 로만
흔적을 남긴다(`[gps] 버림 — …m / …ms (파생 …m/s · 기기 …m/s), 정확도 …m`).
최소 이동거리에 걸린 좌표는 일부러 안 찍는다 — 제자리에 서 있으면 매 좌표가 걸려
로그가 밀려나고, 이쪽은 설계대로 버리는 것이다.

**저장**: `t`·`e` 와 같다. DB 칼럼 하나에 든 JSON 문자열에 키가 붙을 뿐이라
스키마 변경·데이터 이전이 없고, 이 값이 없는 예전 기록도 그대로 읽힌다.

#### 6-4. 사진의 서버 보존 (Storage) — 2026-09-25

**사진만 올린다.** 2026-09-12 에는 "커버 이미지를 서버에 올리지 않는다"고 정했고,
그 근거는 *"route 좌표만 있으면 어디서든 다시 렌더할 수 있다"* 였다. 자동 생성
경로 이미지에는 맞는 말이지만 **사용자가 찍은 사진에는 성립하지 않는다** —
좌표로 복원할 수 없어 기기를 잃거나 앱 데이터를 지우면 영구 소실이다
(2026-09-23 결정). `route_*.png` 는 계속 올리지 않는다.

| | |
|---|---|
| 버킷 | `run-covers` — **private**, 2MB 상한, `image/jpeg` 만 |
| 객체 경로 | `{auth.uid()}/{run_id}.jpg` |
| 정본 SQL | `supabase/migrations/20260925010000_create_cover_storage.sql` |
| 코드 | `services/storage/cover_storage.dart` (업로드 · 파일 이름 규칙) |

**`cover_image_url` 에는 URL 이 아니라 Storage 객체 경로가 들어간다.** 버킷이
private 이라 공개 URL 이 없고, signed URL 은 만료돼 저장해둘 값이 아니다. 경로만
있으면 나중에 어떤 방식으로든 꺼낼 수 있다. 로컬의 `coverImageUrl` 도 파일
경로를 담고 있어 성격이 같다(칼럼 이름만 `url` 이다).

**화면에 안 걸려 있는 사진도 올린다.** 대표 이미지를 경로로 되돌려도 사진 파일은
남겨두는 정책(27-28 의 자유 전환)이라, "지금 표시 중인 것만" 올리면 그 사진이
보존에서 빠진다. `cover_image_type` 이 어느 쪽을 보여줄지 따로 들고 있다.

**업로드 시점은 동기화 큐다.** 사진을 고르면 로컬에 즉시 복사·저장되고, 그 기록의
`syncedAt` 을 비워 업로드 대기로 되돌린다. 이 마지막 단계가 없으면 서버 값이 옛
것으로 남는다 — `Run.toCompanion()` 에 `syncedAt` 이 없어 `upsertRun` 이 그 칸을
건드리지 않기 때문이다(2026-09-23 실측, `AppDatabase.markUnsynced` 주석 참조).
오프라인이어도 등록은 막지 않는다(`offline-handling.md` 2 케이스 D 정정).

**사진 업로드가 실패해도 기록은 올라간다.** 파일이 사라졌으면 사진 없이 행만
올린다 — 사진 한 장 때문에 기록을 못 올리고 재시도를 무한히 도는 쪽이 더 나쁘다.
반대로 Storage 가 응답하지 않는 등의 예외는 그 건 전체를 실패로 보고 기존 정책대로
재시도한다(`offline-handling.md` 4).

> ⚠️ **되받는 경로는 아직 없다.** `run_sync_service` 는 `upsert` 뿐이라 서버에서
> 기록을 내려받지 않는다. 그래서 **기기를 바꾸면 사진이 되살아나지 않는다** —
> 기록 자체가 비어 있어 사진이 붙을 데가 없다. 지금 하는 것은 *보존*이고, 복원은
> 기록 다운로드 기능이 생길 때 함께 완성된다.

  - 🟢 **읽는 방법 — MethodChannel 직접 연결** (`battery_plus` 안 씀).
    Flutter 에 `isPowerSaveMode` 공개 API 가 없어 채널이 필요한데, 호출이
    한 줄이고 **버전 판정(`SDK_INT <= 28`)까지 같은 자리에서 끝난다.**
    의존성을 늘릴 값이 아니라고 봤다. 정본: `MainActivity.kt`.
  - 🟢 **적용 범위 — Android 9(API 28) 이하 + 절전 켜짐일 때만.**
    Android 10 부터는 이 동작이 없어, 버전을 안 보면 최신 기기 사용자가
    **아무 문제 없는데도 경고를 본다.**
  - 🟢 **차단하지 않는다 — 경고만 한다.** 배터리 최적화 제외(6)·알림 권한과
    같은 계열이다. 단 **'설정 열기' 를 고르면 START 를 하지 않고 멈춘다** —
    끄러 보내놓고 그대로 시작하면 보낸 의미가 없다. '그냥 시작' 은 바로 뛴다.
  - 🟢 **2026-09-27 실기기 검증 완료** (노트8, Android 9):
    | 조건 | 결과 |
    |---|---|
    | 절전 ON + START | 안내 팝업이 뜬다 |
    | '설정 열기' | 삼성 `BatterySaverSettingsActivity` 로 이동, START 안 함 |
    | 절전 OFF + START | **팝업 없이 카운트다운 시작** |
  - **제조사 자체 절전은 이 안내가 잡지 못한다.** `isPowerSaveMode()` 는
    안드로이드 표준 절전만 읽는다. 6 의 [미검증] 항목은 그대로 남는다.
- 백그라운드 중 OS가 메모리 부족 등으로 앱을 강제 종료한 경우, 진행 중이던
  러닝 데이터 복구 방법 → 🟢 **확정 (2026-09-15)**
  - 추적 중 **10초마다** 진행 중 러닝(좌표·거리·경과시간·일시정지 여부)을
    로컬 DB `ActiveRuns` 테이블에 **한 행으로 덮어쓴다.** 최대 손실은 10초
    (약 30m) — 10km 기록에서 0.3%이고, 정상 종료 시 손실은 0이다.
  - 앱 시작 시 스냅샷이 있으면 **묻지 않고 조용히 이어붙이고** 달리기 탭으로
    보낸다. 포그라운드 서비스가 붙은 뒤로는 드물게만 타는 경로라, 확인 팝업은
    정상 동작을 비정상처럼 보이게 만든다.

    추적하지 못한 구간이라, 더하면 경로에 없는 거리가 잡혀 페이스만 왜곡된다.
  - 🟢 **복원은 항상 일시정지 상태로 한다 (2026-09-19 확정).** 스냅샷이
    running 이었더라도 마찬가지다. 복원되는 시점의 사용자는 이미 뛰기를 멈춘

      포함하지 않는다.**

    보내고 복원은 뒤따르게 해, 되살아나면 그때 달리기 탭으로 넘긴다.
    스플래시는 사용자가 빠져나올 수단이 없는 화면이라 막히면 앱이 갇히는데,
    그걸 막으려 두었던 3초 타임아웃이 **기기 재부팅 직후 첫 실행에서 터져
    진행 중이던 러닝을 통째로 잃었다**(2026-09-18 실측). 홈은 탭바가 있어
    갇히지 않으므로 시간 제한 없이 기다려도 안전하다.
    - 대가로 "홈이 잠깐 보였다가 달리기 탭으로 전환"되는 구간이 생긴다.
      러닝을 잃는 것보다 가벼운 대가로 판단했다.
  - 마지막 스냅샷이 **6시간**보다 오래됐으면 이어 뛰지 않고 그대로 기록으로
    확정한다. 풀코스 완주자도 넉넉히 커버하는 값.
    - 🟢 **단, 아무것도 안 담긴 스냅샷은 기록으로 만들지 않는다
      (2026-09-25 확정).** 달린 시간·거리·좌표가 **셋 다 비었으면** 기록을
      만들지 않고 스냅샷만 버린다.
      - 스냅샷은 10초 주기 말고 **시작 직후에도 한 번** 저장된다("시작하자마자
        죽는 경우"를 덮으려고). 그래서 START 를 누른 찰나에 앱이 죽으면 셋 다
        빈 스냅샷이 남고, 6시간 뒤 `0.0km · 00:00 · 좌표 없음` 짜리 기록이
        생겨 **서버까지 올라간다**(2026-09-25 실측).
      - **`records.md` 의 0km 정책과 충돌하지 않는다.** 그쪽은 "거리 0 도
        저장은 막지 않는다"인데, 뛰었는데 GPS 를 못 잡은 기록은 **시간이
        쌓여 있어**(예: 1분 37초 · 0.00km) 이 조건에 안 걸린다. 여기서
        거르는 건 달린 시간조차 0 인, 기록이랄 게 없는 경우다.
      - 기록을 삭제할 수단이 없으므로(`records.md` 22) **안 만드는 것이
        유일한 수단**이다.
  - 스냅샷 삭제는 정식 기록 저장(`upsertRun`)이 **성공한 뒤에** 한다. 순서가
    반대면 저장 직전에 죽는 찰나에 기록이 사라진다.
  - 좌표를 한 행씩 append 하지 않는 이유: 쓰기량은 append 가 유리하지만
    (풀코스 기준 ~750KB vs ~200MB) 둘 다 문제되는 절대량이 아니고, 일시정지를
    뺀 거리는 좌표만으로 복원할 수 없어 어차피 세션 메타를 따로 관리해야 한다.
- 경로 렌더 이미지 생성 실패 시(GPS 포인트 부족 등) 대체 이미지 →
  **[미확정]** (예: 브랜드 로고 플레이스홀더로 대체)
- 사진 등록 후 다시 미등록 상태로 되돌릴 수 있는지 → 가능하다고 가정
  (경로 이미지로 재전환)

### 9. 음성 안내 (2026-09-27 신설)

출발과 1km 구간, 종료를 음성으로 알린다. 구현은
`features/run/data/voice_guide.dart`, 문구 검증은 `test/voice_guide_test.dart`.

#### 9-1. 무엇을 언제 말하나

| 시점 | 멘트 | 실측 길이 |
|---|---|---|
| 출발 | `러닝을 시작합니다` | 1.4초 |
| 1km | `1킬로미터, 6분 28초` | 2.2초 |
| 2km 부터 | `2킬로미터, 구간 6분 28초, 평균 6분 41초` | 4.3초 |
| 종료 | `러닝을 종료합니다. 전주까지 142.6킬로미터 남았습니다` | 5.1초 |
| 도시 도착 | `러닝을 종료합니다. 전주에 도착했습니다` | 3.4초 |

길이는 2026-09-27 노트8(삼성 TTS)에서 실제로 읽힌 값이다.

- **1km 에서는 평균을 읽지 않는다.** 첫 구간은 구간 페이스와 평균이 같은 값이라
  같은 숫자를 두 번 듣게 된다.
- **종료 때 거리·시간을 읽지 않는다.** 요약 화면에 크게 떠 있다. 반대로
  **여정 잔여 거리는 그 화면에 없어서**, 음성이 그걸 알리는 유일한 자리다.
- **일시정지·재개는 안내하지 않는다.** 방금 누른 행동이라 정보가 없다.
  (출발은 다르다 — 카운트다운 뒤 **자동으로** 시작돼 폰이 이미 주머니에 있다.)
- **말투는 `~습니다` 로 통일한다**(2026-09-27 사용자 결정). 화면 문구는
  해요체지만, 한 문장 안에서 "종료합니다 … 남았어요" 처럼 섞이면 어색하다.

#### 9-2. 문구 표기 규칙

TTS 가 읽을 문장이라 **화면 표기를 그대로 넘기면 안 된다.**

| 규칙 | 이유 |
|---|---|
| 기호 금지 — `6'28"` ✗ → `6분 28초` ✓ | 따옴표를 단위로 못 읽는다 |
| 단위는 한글 — `km` ✗ → `킬로미터` ✓ | 영문 약어는 엔진마다 다르게 읽는다 |
| 0초는 뺀다 — `6분 0초` ✗ → `6분` ✓ | 정각일 때만 생기는데 어색하다 |
| 소수는 첫째 자리까지 | `3.24` → `3.2킬로미터` |

이 규칙들은 **테스트로 막는다**(`voice_guide_test.dart` 14건). 기호나 `km` 가
문장에 섞이는 건 들어보기 전에는 모르기 때문이다.

#### 9-3. 구간 시각은 보간한다

좌표가 km 경계에 딱 떨어지는 일은 없다. 도착 좌표의 시각을 그대로 쓰면 구간이
실제보다 길어지고 오차가 뒤로 계속 밀린다. 그래서 **기록 화면의 구간 페이스
(`km_splits.dart`)와 같은 방식으로 보간한다** — 음성과 화면이 다른 숫자를
말하면 그게 곧 버그 신고다.

**한 번에 2km 이상을 넘겼으면 마지막 것만, 페이스 없이 읽는다.** 연달아
"1킬로미터" "2킬로미터" 를 읽으면 소음이고, 그렇게 벌어진 구간은 페이스도
믿을 값이 아니다.

#### 9-4. 목소리는 기기 설정을 따른다

**앱이 음성을 싣지 않는다.** 기기에 설치된 TTS 엔진과 사용자의 시스템
설정(엔진·속도·톤)을 그대로 쓴다. 삼성헬스도 같은 방식이다("음성 안내는 단말
시스템의 TTS 설정에 따른다").

- **속도·톤을 코드에서 덮어쓰지 않는다.** 덮어쓰면 다른 앱과 우리 앱만 다르게
  들린다.
- **한국어 음성 데이터가 없으면 조용히 끈다.** 엔진 설치와 한국어 데이터는
  별개다. 알림 권한·절전 모드와 같은 원칙으로, 음성이 안 되는 것이 러닝을
  막아서는 안 된다.

2026-09-27 노트8 확인: 삼성 TTS 엔진(v3.5.01.69), 한국어 음성이
**`기본 음성 1` 하나뿐이라 성별 선택지가 없다.** 로그상 `kor-KOR-f00`
(여성), `Speed[100] Pitch[100]`(시스템 기본값 그대로). 기기마다 다를 수 있다.

#### 9-5. 남은 것

- 🟡 **읽는 속도 — 판단 보류 (2026-09-27)** — 노트8 에서 들어보니 **살짝
  빠르게 느껴진다**(사용자). 다만 우리는 속도를 건드리지 않았고 로그상
  `Speed[100]`, 즉 **기기 시스템 설정 그대로** 나간 값이다. 기기·엔진마다
  체감이 다를 수 있어 **다른 기기에서 더 들어본 뒤 정한다.** 선택지는 셋:
  ① 그대로 둔다(시스템 설정 존중, 지금 방식) ② 앱에서 조금 늦춘다
  (9-4 의 "덮어쓰지 않는다" 와 충돌하므로 근거가 필요하다) ③ 설정에 속도
  조절을 둔다(Runkeeper 식, MVP 이후).
  **확인 방법**: 디버그 빌드에서 달리기 탭의 러닝 타입 카드를 **길게 누르면**
  다섯 문장을 이어서 들을 수 있다. 밖에 나가지 않아도 된다
- 🟡 **음소거 스위치** — 코드에 `muted` 플래그만 있고 UI 가 없다.
  **설정을 저장할 곳이 앱에 없어서**(drift 테이블은 `Runs`·`ActiveRuns` 둘뿐)
  저장 방식이 미정이다. 칼로리 계산에 필요한 체중 입력과 **같은 자리**가 되므로
  함께 정하는 편이 낫다
- 🟡 **음악 덕킹 미검증** — 음성이 나올 때 음악을 줄이고 얹을지. 업계 앱들도
  문서화하지 않는 영역이라 **음악을 틀어놓고 직접 들어봐야** 한다.
  참고: 음악을 **멈추는** 방식은 재생이 자동 복구되지 않는 사고가 보고돼 있다
- 🔴 **iOS 미검증** — Mac 이 없어 `speak` 를 **안드로이드에서만 켜뒀다.**
  iOS 는 오디오 세션 설정이 따로 필요하다
- **수동 트리거**(화면을 눌러 즉시 현재 상태 듣기) — Runkeeper 에 있는 기능.
  달리는 중 화면을 보는 것보다 안전하다. MVP 이후

### 10. 출발 전 날씨 (2026-10-03 신설 — 기상청 연동)

출발 전 화면의 날씨 카드 `☀️ 15°C 맑음` 의 규칙. 화면 구조의 정본은 Figma
(`figma-alignment.md` ⑨ — 체감온도는 2026-09-27 에 뺐다). 미세먼지(에어코리아)는
다음 단계에서 이 장에 붙인다.

#### 10-1. 어디서 무엇을 받나

| 값 | API (기상청 단기예보 조회서비스) | 항목 |
|---|---|---|
| 기온 | 초단기실황 `getUltraSrtNcst` | `T1H` (정수로 반올림) |
| 비·눈 | 초단기실황 | `PTY` 1·5 비 / 2·6 비/눈 / 3·7 눈 |
| 맑음·구름많음·흐림 | 초단기예보 `getUltraSrtFcst` | 가장 이른 시각의 `SKY` 1 / 3 / 4 |

- 비·눈이 오면 하늘상태보다 우선한다 — 그때는 예보를 부르지 않는다
- 위경도 → 격자(nx, ny)는 기상청 공개 LCC 변환식. 서울시청 = (60, 127)
- 기상청 발표 시각은 **한국 시각(KST)** 으로 계산한다. 기기 시간대가 달라도 맞다
- 인증키는 `env.json` 의 `DATA_GO_KR_KEY` 하나 (에어코리아도 같은 키).
  앱에 박히는 것은 2026-09-20 결정 — 노출 피해가 "호출 한도 소진" 수준이다

#### 10-2. 언제 다시 받나 — 다음 갱신 시각까지 (2026-10-03 사용자 결정)

- 실황은 매시 정각 자료가 40분 뒤에, 예보는 매시 30분 자료가 45분 뒤에 나온다
- 받은 값은 **둘 중 늦게 나오는 다음 자료 시각까지** 다시 쓴다 → 대략
  **시간당 1회**(매시 45분 무렵). "고정 30분 / 고정 1시간" 은 최대 1.5~2시간
  묵은 값을 보이게 돼서 택하지 않았다
- 기억은 **메모리**에만 한다. 앱을 다시 켜면 한 번 새로 받는다
- 격자(5km)가 바뀌면 다시 받는다. 좌표가 조금 흔들리는 것으로는 안 부른다
- 하늘상태만 실패하면 **기온만** 보이고, 10분 뒤 다시 시도한다
- 실패는 기억하지 않는다 — 탭을 다시 열면 다시 부른다
- 한도: 기상청은 오퍼레이션별 일 10,000건(개발계정). 한 번에 최대 2건 쓴다

#### 10-3. 못 보여줄 때 — 가짜 값을 채우지 않는다

| 상황 | 화면 |
|---|---|
| 불러오는 중 | 값 자리에 뼈대(`SkeletonBox`) |
| **위치를 모른다** (권한 전 · 마지막 위치 없음) | "불러오지 못했어요" — **서울 날씨로 대신하지 않는다** (2026-10-03 사용자 결정). 권한을 묻는 시점은 START 라 처음 설치한 사람은 첫 달리기 전까지 이 상태다 |
| 키가 없다 (`env.json` 누락) | "불러오지 못했어요" |
| 10초 안에 응답이 없다 · 오류 | "불러오지 못했어요". 공공데이터 API 는 가끔 15초 넘게 응답이 없다(2026-10-03 확인) |

- 요청 URL 에 인증키가 들어가므로 **오류 로그에 URL·예외 메시지를 남기지 않는다** (예외 타입만)

#### 10-4. 출처 표시

공공데이터포털 이용허락이 **저작자표시**(공공누리 1유형)다. 출발 전 카드는
자리가 빠듯해 **프로필 하단 버전 표시 아래**에 적는다 (2026-10-03 사용자 결정,
`profile-settings.md` 3).
