## 오프라인 처리 (Offline Handling)

**최종 수정일**: 2026-09-19
**상태**: 🟢 정책 확정
**담당**: 기획/디자인 - OOO / 개발 - OOO
**연관 문서**: `run-flow.md`, `global-states.md`, `online-marathon.md`

### 1. 개요

네트워크 연결이 끊긴 상태에서 앱의 각 기능이 어떻게 동작할지 정의한다.
GPS 트래킹 자체는 네트워크가 필요 없는 기기 기능이므로, 러닝의 핵심
동작은 오프라인에서도 끊기지 않는 것을 원칙으로 한다.

### 2. 케이스별 정책

**케이스 A — 러닝 중 오프라인**
- GPS 추적은 네트워크와 무관하게 정상 동작 (전혀 영향 없음)
- 날씨/미세먼지 카드처럼 네트워크가 필요한 부가 정보만 "불러오지 못했어요"
  상태로 표시 (`global-states.md`의 인라인 에러 패턴 재사용)

**케이스 B — 러닝 종료 시 오프라인 (서버 저장 실패)**
- 러닝 데이터(경로, 거리, 시간 등)는 **기기 로컬에 우선 저장**
- 서버 업로드는 백그라운드에서 **동기화 대기 큐**에 넣고, 네트워크 재연결
  시 자동 재시도
- 결과 화면(RunDetailView)은 로컬 데이터로 정상 표시, 상단에 "동기화 대기
  중" 작은 배지 노출
  > **구현 노트(2026-09-13 → 2026-09-19 해소)**: `RunDetailView` 가 없던 동안은
  > **기록 탭의 기록 카드**에 먼저 붙여뒀다(`records.md` §3 뱃지 표). 2026-09-19
  > 에 기록 상세 화면이 생기면서 **문서가 원래 지정한 자리에도 적용**했고,
  > 예고한 대로 같은 provider(`pendingSyncRunIdsProvider`)를 재사용한다.
  > 카드 쪽 뱃지는 그대로 둔다 — 목록에서 바로 보이는 편이 낫다.
  >
  > 판정은 `Run` 모델이 아니라 대기 id 명단(`watchUnsyncedIds`)으로 한다 —
  > 모델에 `syncedAt` 을 실으면 대표 이미지 수정이 `upsertRun` 을 탈 때 옛 값이
  > 덮어써져 수정본이 서버에 반영되지 않는다.
- 온라인 마라톤 참여 중이었다면, GPS 인정 판정(서버 검증 포함 시)도 동기화
  완료 후에 이루어짐 — 사용자에게는 "순위 반영은 동기화 후 진행돼요" 안내

**케이스 C — 기록/콘텐츠 조회 중 오프라인**

> 🟢 **정정 (2026-09-19)**: 원래 이 자리에 "기록 탭은 마지막으로 불러온 데이터를
> 캐시로 표시하고 '최신 정보가 아닐 수 있어요' 배너를 노출한다"고 적혀 있었다.
> 2026-08-15 작성본이 **local-first 확정 전의 가정**("기록을 서버에서 불러온다")을
> 담고 있었던 것이다. 실제 구현과도, 같은 문서 §4 의 "로컬이 1차 진실 소스"와도
> 어긋나 바로잡는다.

- **기록 탭 — 캐시가 아니라 원본이다.** 서버에서 불러오지 않고 로컬 drift DB 를
  직접 관찰한다. 오프라인이어도 데이터가 완전하므로 **"최신 정보가 아닐 수
  있어요" 배너는 달지 않는다** — 사실이 아닌 안내가 된다. 연결 상태는 §3 전역
  오프라인 배너로만 알린다.
  - 아직 서버에 못 올린 기록은 '동기화 대기' 배지로 따로 표시된다(케이스 B).
    이건 **조회의 문제가 아니라 업로드 상태 표시**라 성격이 다르다.
- **콘텐츠 탭**(테마 러닝/온라인 마라톤 목록): 캐시가 없으면 기존 에러 UI
  ("불러오지 못했어요" + 다시 시도 버튼, `global-states.md`) 노출.
  - 구현 노트(2026-09-19): 지금은 목록이 앱에 내장된 샘플이라 오프라인에서도
    그대로 뜬다. 다만 카드 이미지가 원격(Unsplash 임시)이라 **이미지만** 실패한다.
    콘텐츠가 서버 데이터로 바뀌면 위 정책이 그대로 적용된다.

**케이스 D — 액션 시도 중 오프라인**
- "START"(러닝 시작): 오프라인이어도 가능 (로컬 트래킹이므로)
- "참가하기"(온라인 마라톤): 서버 등록이 필요하므로 오프라인 시 버튼
  비활성화 + "네트워크 연결 후 다시 시도해주세요" 안내
- 대표 이미지 교체, 닉네임 변경 등 서버 저장이 필요한 액션도 동일하게
  오프라인 시 비활성화

> 🟢 **정정 (2026-09-25) — 대표 이미지 교체는 오프라인에서도 된다.**
> 위 문장도 케이스 C 와 같은 뿌리의 문제였다. 2026-08-15 작성본이 **local-first
> 확정 전의 가정**("대표 이미지 교체는 서버 저장이 필요한 액션")을 담고 있었다.
>
> 실제로는 사진을 고르면 **앱 문서 폴더에 즉시 복사되고 로컬 DB 가 갱신된다.**
> 서버 업로드는 `syncedAt` 을 비워 동기화 큐에 얹는 후행 처리라, 오프라인이어도
> 막을 이유가 없다 — 재연결되면 §3 대로 자동으로 올라간다. 막으면 오히려
> "로컬이 1차 진실 소스"(§4)와 어긋난다.
>
> **"참가하기"(온라인 마라톤)는 위 정책이 그대로 맞다.** 그쪽은 서버에 자리를
> 잡는 일이라 로컬에서 먼저 확정할 수 없다. 차이는 *로컬로 완결되는 액션인가*
> 이고, 대표 이미지는 완결되지만 마라톤 참가는 안 된다(2026-09-25 사용자 결정).

### 3. 전역 네트워크 상태 배너

- 앱 전역에서 네트워크 연결 여부를 감지
- 끊기면 화면 상단에 얇은 "오프라인" 배너 노출 (모든 화면 공통)
- 재연결되면 배너 사라지고, 대기 중인 동기화 큐가 있으면 자동 처리 시작

### 4. 데이터 요구사항 (개발자 확인 필요 영역)

```typescript
type SyncQueueItem = {
  id: string;
  type: "run_upload" | "cover_image_update" | "nickname_update"; // 확장 가능
  payload: unknown;
  createdAt: string;
  retryCount: number;
};
```

- 로컬 저장소(디바이스 DB) 필요 — 러닝 데이터는 서버 저장 전까지 로컬이
  1차 진실 소스(source of truth)
- 재시도 정책: 🟢 **확정(2026-09-12)** — 횟수 제한 없이 계속 재시도한다.
  간격만 30초 → 1분 → 5분 으로 늘리고 이후 5분을 반복(앱 실행 중에만).
  근거: 장시간 오프라인(산·지하)에서 횟수로 포기하면 그 기록은 영영 서버에
  올라가지 못한다. "기록은 잃지 않는다"가 상위 원칙.
- 동기화 성공 후 로컬 캐시 정리 시점: 🟢 **확정(2026-09-12)** — 정리하지 않고
  영구 보관한다. 로컬이 1차 진실 소스이고, 기록 탭은 오프라인에서도 전부 보여야
  한다(위 케이스 C). 러닝 1건은 수 KB 수준이라 용량 부담이 없다.

> **구현 노트(2026-09-12)**: 위 `SyncQueueItem` 별도 테이블은 MVP 에서 도입하지
> 않는다. 현재 올릴 대상이 `run_upload` 하나뿐이라, 로컬 `runs` 테이블의
> `synced_at` 컬럼(null = 대기)으로 대기 목록을 표현한다. 큐 테이블은 같은
> 데이터를 두 곳에 두어 원본과 복사본이 어긋나는 비용만 생긴다.
> `cover_image_update`·`nickname_update` 처럼 러닝 행에 플래그를 붙일 수 없는
> 작업이 실제로 생기면 그때 큐 테이블을 **추가**한다(플래그 방식과 공존 가능).
> 재시도 횟수/간격은 앱 실행 중 메모리 상태로만 관리하므로 `retryCount` 를
> DB 에 둘 필요가 없다.

### 4-1. 내려받기 — 서버 기록을 기기로 (2026-10-02 확정)

**목표: 같은 계정이면 어느 폰에서 봐도 같은 기록이 보인다.** 2026-10-01 까지
동기화는 업로드 단방향이라, 재설치·기기 변경 시 서버에 멀쩡히 있는 기록을
기기가 모르고 홈·기록·배지가 0 으로 보였다(2026-09-13 노트 §3-5 에서 발견).

| 항목 | 정책 |
|---|---|
| 언제 | **로그인 직후 + 앱 시작 시.** 업로드와 같은 시점이다. 당겨서 새로고침은 MVP 에서 두지 않는다 |
| 범위 | 내 기록(`user_id = auth.uid()`) **전부.** 여정·스트릭·배지가 누적으로 계산돼 일부만 받으면 숫자가 틀린다 |
| 경로(route) | **함께 받는다.** 기록 상세 지도·경로 이미지에 필요하다 |
| 대표 사진 | **미리 받지 않는다.** 상세 화면을 열 때 Storage 에서 바로 표시한다. 오프라인이면 안 보인다 |
| 합치는 규칙 | **로컬에 없는 id 만 추가한다. 이미 있는 id 는 로컬을 그대로 둔다.** 받은 행은 `synced_at` 을 채워 다시 업로드되지 않게 한다 |

**합치는 규칙의 근거**: 기록은 삭제·수치 수정이 불가하므로(`records.md` 2)
같은 id 면 수치도 같다. 로컬이 1차 진실 소스라는 원칙(§4)과도 맞는다.
유일한 예외는 **대표 이미지 전환**(사진↔경로)인데, 두 폰에서 다르게 바꾸면
로컬 쪽이 이긴다. 드물어서 감수한다.

> **구현 (2026-10-02)**: `RunSyncService.pullNow()` 가 1000건씩 페이지를 넘겨
> 전부 읽고 `AppDatabase.insertDownloadedRuns()` 가 합친다. 호출은 스플래시 ·
> 로그인 직후 · 재연결 세 곳(업로드와 같은 자리). 서버 사진은 `cover_image_url`
> 이 Storage 경로(`{uid}/{runId}.jpg`)라 상세 화면이 `isRemoteCoverPath` 로
> 가려 signed URL 로 띄운다. 이 경로는 재업로드 때 그대로 다시 올라간다 —
> null 로 올리면 서버의 사진 경로가 지워진다. 합치는 규칙은
> `test/run_download_test.dart` 가 건다.

**한계 — "조금 늦게 같아진다"** (실시간 동기화가 아니다)
- 폰 B 에서 뛴 기록은 B 가 **업로드한 뒤**, 폰 A 가 **앱을 다시 켤 때** 보인다.
  켜둔 채로는 바로 뜨지 않는다
- B 가 오프라인이라 아직 못 올린 기록은 A 에 안 보인다
- 새 폰에서 오프라인으로 처음 로그인하면 기록이 비어 보이고, 연결 후 채워진다
- 다른 폰에서 뛴 기록의 대표 사진은 오프라인에서 안 보인다

**로그아웃하면 로컬 기록을 비운다** (같은 날 확정, 정본은 `profile-settings.md`
'로그아웃'). 로컬 `runs` 에는 소유자 컬럼이 없어서, 비우지 않으면 한 폰에서
다른 계정으로 로그인했을 때 **앞 계정의 기록이 보이고, 못 올린 기록이 뒤 계정으로
업로드되고**, 내려받기가 붙으면 두 계정 기록이 섞인다. 다시 로그인하면 내려받기로
돌아온다.

### 5. 엣지 케이스

- 동기화 대기 중인 러닝이 여러 개 쌓인 경우(연속 오프라인 러닝) → 오래된 것부터
  순서대로 업로드하되, 🟢 **실패해도 다음 건으로 넘어간다(2026-09-12 확정)**.
  실패한 건은 대기 상태로 남겨 다음 주기에 재시도. 근거: 특정 1건이 서버에서
  계속 거부당할 때 그 뒤의 모든 기록이 함께 막히는 상황이 더 나쁘다.
- 앱 삭제/재설치 시 동기화 안 된 로컬 데이터 유실 가능 → 이 리스크는
  감수하는 것으로 가정 (일반적인 모바일 앱 관례). **이미 올라간 기록은
  재로그인 시 내려받기로 복원된다**(§4-1, 2026-10-02)
